# Fuzz Testing (`fuzz`)

The `fuzz` crate (`cargo-fuzz` + `libfuzzer-sys`) is a Cargo workspace of its own, not a member of the root one, so the root's `cargo metadata`, which FOSSA and cargo-deny read, leaves out `libfuzzer-sys`. It has its own `Cargo.lock` in git. Dependabot updates only `libfuzzer-sys` in `fuzz/`: the fuzz targets' path dependencies inherit requirements from the root `[workspace.dependencies]`, and a Dependabot update of one of those from `fuzz/` would edit the root `Cargo.toml` with only `fuzz/Cargo.lock` to match it. So the rest of `fuzz/Cargo.lock` falls behind the root lock between releases. No CI job checks it, and cargo-deny reads only the root graph: `/cut-release` is the only check, and it has a stale lock refreshed in a PR of its own before the version bump. On a stale lock, `just clippy` and `cargo fuzz` rewrite `fuzz/Cargo.lock` in the working tree; commit that rewrite with your change, or restore it with `git restore fuzz/Cargo.lock`. Its `bytes`, `rama`, `tokio` and `url` requirements repeat the root's `[workspace.dependencies]`, so change both together, also in a Dependabot PR, which changes only the root's. `just clippy` and `just fmt` reach it through `--manifest-path fuzz/Cargo.toml`, and its release profile is in `fuzz/Cargo.toml`. CI runs its targets through `fuzz.yml` (see `.github/AGENTS.md`), and you can run any of them locally. It requires the nightly toolchain, which `just` targets invoke explicitly (`cargo +nightly fuzz ...`); you don't need to switch your default toolchain.

```shell
just cargo-fuzz +args        # cargo +nightly fuzz {{args}}, with LTO off as in fuzz-ci
just fuzz-request-decode     # fuzz_request_decode, 60s
just fuzz-member-metadata    # fuzz_member_metadata, 60s
just fuzz-generate-seed      # (re)generate the corpus seed files, see below
just fuzz-ci <tier> [target]  # the targets of a tier in fuzz/ci-targets.json, each for its budget

cargo +nightly fuzz list                             # list all targets
just cargo-fuzz run <target> -- -max_total_time=60      # fuzz one target
just cargo-fuzz run <target> fuzz/artifacts/<target>/<crash-file>     # replay a saved crash
```

Three target shapes, all in `fuzz/fuzz_targets/`:
- **`fuzz_request_decode` / `fuzz_response_decode` / `fuzz_varint` / `fuzz_deflated_batch` / `fuzz_member_metadata`** — fuzz raw bytes straight through the wire decoder/encoder, no `Storage` involved.
- **`fuzz_<api>_storage`** (the majority, ~22 targets, one per Kafka API like `fuzz_fetch_storage`, `fuzz_create_topics_storage`) — build an arbitrary typed request (via `nisshi-sans-io`'s `arbitrary` feature) and run it end-to-end through the real `*Service` against an in-memory `StorageContainer` (storage starts empty every execution), to catch panics/invariant violations in service and storage logic rather than the decoder.
- **`generate_seeds`** (plain `fn main`, not a fuzz target) — writes hand-built binary seed files into `fuzz/corpus/<target>/`; rerun it after adding a new seed case.

`nisshi-fuzz-harness` provides the shared `api_version`/`check_request`/`check_response` helpers used by the storage targets. It is a crate of its own, without libFuzzer and without binaries, so `just test-workspace` builds and tests it with every other workspace crate. Each target takes `(u16, Request)`, and `api_version::<T>(selector)` maps the `u16` onto one of the versions of that API that nisshi routes (`routable_range` in `nisshi-service`: the protocol's own range, narrowed for Produce, ListOffsets and AddPartitionsToTxn), so every version a client can reach is fuzzed, not only the latest. `check_request` encodes the value at that version, decodes it, re-encodes the decoded value, and asserts the two encodings are byte-identical; `check_response` does the same for the service's response, at the same version. A failure names the API key and the version. They deliberately do **not** assert the decode equals the original fuzzed value: a sans-io codec is not required to be lossless against an arbitrary in-memory value (e.g. every generated sequence field is `Option<Vec<T>>` regardless of wire nullability, so a mandatory array left at `None` is wire-equivalent to `Some(vec![])` but not `PartialEq`). The property that must hold is that the decoder's output re-encodes to the same bytes. `check_request` returns the decoded request, so a target serves the service what a client could actually send instead of the raw fuzzed value. It returns `None` when the encoder refuses with `Error::MandatoryFieldUnset` for a field that `may_be_unset` in `nisshi-fuzz-harness/src/lib.rs` allows (today only a Metadata topic's `Name` below v10); a target returns on `None`. A refusal for any other field panics, so a version can't stop being fuzzed unnoticed. For a response, `MandatoryFieldUnset` is a failure: a service answered with a field that version requires left unset. `nisshi-fuzz-harness/tests/versions.rs` drives `check_request` over every routed version of every storage target's API without libFuzzer, and serves Metadata against `memory://` at every version.

`fuzz/corpus/`, `fuzz/artifacts/` (crash reproducers) and `fuzz/.gitignore`'s `target`/`coverage` are all untracked — rebuild the corpus locally with `just fuzz-generate-seed` plus whatever `cargo +nightly fuzz run` accumulates. If you fix a bug found by fuzzing, replay every existing artifact for that target (`just cargo-fuzz run <target> fuzz/artifacts/<target>/<crash-file>`) to confirm the fix, not just the one input that was being worked on. A storage target reads two bytes for the version selector before the request, so an artifact or corpus entry saved before that change decodes to a different request and replays clean: replay such an artifact on a checkout from before it. The `fuzz-corpus-*` cache that `fuzz.yml` restores starts these targets over for the same reason.
