# Changelog

All notable changes to this project will be documented in this file.

This file is generated from the commit history when a release is cut. Pull requests don't edit it; describe user- and operator-visible changes in the pull request description instead, which becomes the body of the commit on `main`.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [0.8.2] - 2026-11-04

### Upgrade notes

- **Auto-created topics now get 1 partition, not 4, and CreateTopics with `num_partitions` of `-1` gets 1, not 3** ([#1203](https://github.com/nisshi-io/solace-nisshi/pull/1203)). Both now follow the new `--num-partitions` setting (`NUM_PARTITIONS`, default `1`), as Kafka's `num.partitions` does. Nisshi can't add partitions to an existing topic, so a topic created with 1 partition keeps 1. To keep 4 partitions for auto-created topics, set `NUM_PARTITIONS=4` before you upgrade. CreateTopics with `-1` then also gets 4. If your environment already exports `NUM_PARTITIONS` for something else, the broker now reads it, and it refuses to start if the value isn't a whole number of at least 1. Metadata auto-creation also changed:
  - `--auto-create-topics-enable` (`AUTO_CREATE_TOPICS_ENABLE`, default `true`) turns it off. With `false`, an unknown name answers `UNKNOWN_TOPIC_OR_PARTITION` and an invalid one answers `INVALID_TOPIC_EXCEPTION`, at every Metadata version.
  - A Metadata request whose unknown names need more than 10,000 partitions in total creates none of them. Each name answers `UNKNOWN_TOPIC_OR_PARTITION`, and the broker logs a warning.
  - A name that collides with an existing topic (`a_b` while `a.b` exists) is not auto-created. It answers `UNKNOWN_TOPIC_OR_PARTITION`, and each broker remembers the refusal for 5 s, so if you delete `a.b`, auto-creation of `a_b` can take up to 5 s longer ([#1238](https://github.com/nisshi-io/solace-nisshi/pull/1238)).
- **A storage URL option whose value doesn't parse now stops the broker at startup** ([#1185](https://github.com/nisshi-io/solace-nisshi/pull/1185)). Before, the engine used the option's default. This covers `batch_min_size` and `batch_max_delay` on `s3://` and `gs://`, and `busy_timeout`, `compaction` and `mode` on `sqlite://`. Values are case-sensitive (`mode=Direct` fails; use `direct`), an empty value such as `?busy_timeout=` is refused, and when an option appears more than once, every occurrence must parse and the last one wins. Before, the first valid one won, so `?mode=direct&mode=mpsc` now selects `mpsc`. Check your storage URLs before you upgrade. The error names the option, the value, the engine and what the option accepts, for example `storage option mode=Direct is not valid for the sqlite engine: give semaphore, mpsc or direct`.
- **A host name in `--listener-url` (`LISTENER_URL`) now binds one address instead of every interface** ([#1181](https://github.com/nisshi-io/solace-nisshi/pull/1181)). The broker resolves the name and binds the first IPv4 address, or the first address if there is no IPv4 address, as Kafka does. For example, a broker started with `tcp://localhost:9092` used to be reachable from other hosts, and now accepts only local clients. A name that doesn't resolve now stops the broker at startup, with an error that names the host. To listen on every interface, set `tcp://[::]:9092` (IPv6 and IPv4) or `tcp://0.0.0.0:9092` (IPv4 only). IP literals and the default listener are unchanged.
- **The `operation` label of the `nisshi_storage_channel_*` metrics is now snake_case** ([#1264](https://github.com/nisshi-io/solace-nisshi/pull/1264)). This affects `nisshi_storage_channel_capacity`, `nisshi_storage_channel_request_duration`, `nisshi_storage_channel_permit_duration`, `nisshi_storage_channel_error`, `nisshi_storage_channel_server_failure` and `nisshi_storage_channel_response_discarded`. For example, `operation="Fetch"` becomes `operation="fetch"` and `operation="ListOffsets"` becomes `operation="list_offsets"`. A query or alert on an old value doesn't fail. It matches nothing, so an alert built on it stays quiet. Update each one, or match both spellings across the upgrade (`operation=~"Fetch|fetch"`). The `operation` field of the storage request channel's log events changes in the same way. Text-format logs no longer quote it, so the read-deadline events go from `operation="fetch"` to `operation=fetch`. Other storage metrics already used snake_case and don't change.
- **A Fetch above the end of the log now answers `OFFSET_OUT_OF_RANGE`, so the consumer applies `auto.offset.reset`** ([#1273](https://github.com/nisshi-io/solace-nisshi/pull/1273)). Before, the broker answered `NONE` with no records, and the consumer waited there. This reverses a 0.7.0 change. With `earliest`, such a consumer replays the retained log. With `none`, the application gets an exception. To find the groups that will reset, look for negative lag in `kafka-consumer-groups --describe` before you upgrade. On memory, S3 and Google Cloud Storage, the broker reads the high watermark again from the store before it answers the error, so a consumer that is only ahead of a cached value isn't reset.
- **Avro keys and values written as object containers with a codec other than `null` now get `INVALID_RECORD`** ([#1182](https://github.com/nisshi-io/solace-nisshi/pull/1182)). Earlier versions accepted `deflate`, and also `snappy` and `zstandard` in builds with the `iceberg` feature. A producer that compresses each record's container, for example with Java's `DataFileWriter.setCodec(...)`, must write with the `null` codec. To compress records, set the producer's `compression.type` instead. `nisshi cat` and `nisshi generator` already write with `null`. See Security.
- **Memory, S3 and Google Cloud Storage: restart idempotent producers that write to a `nisshi.lake.sink` topic during the upgrade** ([#1215](https://github.com/nisshi-io/solace-nisshi/pull/1215)). Lake-sink topics now check the producer sequence, as other topics already do. Earlier versions stored no sequence for these partitions, so a producer that keeps running across the upgrade sends a batch with a sequence above 0 and gets `OUT_OF_ORDER_SEQUENCE_NUMBER`. A producer that starts after the upgrade isn't affected.
- **S3 and Google Cloud Storage: the first timestamp lookup on each partition rebuilds its time index once** ([#1198](https://github.com/nisshi-io/solace-nisshi/pull/1198)). The first `offsetsForTimes` or `kafka-consumer-groups --reset-offsets --to-datetime` on each partition after the upgrade lists, reads and decodes every batch of that partition. On a large partition, that lookup can take longer than the client's `request.timeout.ms`. A retry is safe. The `time index backfill: starting` log line (with `older_version = true`) and its `committed` line show each rebuild. Upgrade every broker that shares a bucket together. While an older broker still produces to a partition, each of its produces makes the next lookup on a newer broker rebuild that partition's index again.
- **`nisshi topic list` now prints a table** ([#1229](https://github.com/nisshi-io/solace-nisshi/pull/1229)). The table has topic names and partition counts, sorted by name, or `No topics.` when there are none. A script that parses the output must add `--output json`, which prints the same JSON as before. Releases up to 0.8.1 don't accept `--output`.
- **`nisshi proxy` no longer queues idempotent, transactional or control batches on a `nisshi.batch=true` topic** ([#1210](https://github.com/nisshi-io/solace-nisshi/pull/1210)). Batches with a log append time aren't queued either. The proxy forwards such a request to the origin straight away, so the `nisshi.batch.timeout_ms` wait doesn't apply to it. The Java producer has idempotence on by default, so expect this for most Java clients. If you turned on `nisshi.batch` to reduce the request rate to the origin, expect that rate to rise. The new `batch_bypassed` counter shows how many requests skip the queue.
- **A Produce whose `acks` is not `-1`, `0` or `1` is now refused** ([#1192](https://github.com/nisshi-io/solace-nisshi/pull/1192)). Every partition answers `INVALID_REQUIRED_ACKS` and nothing is stored, as with Kafka. The broker logs each such request at `warn`. A client configured with a numeric `acks` above 1 must use `all`, `-1`, `0` or `1`.
- **OffsetCommit and TxnOffsetCommit refuse commit metadata longer than 4096 UTF-16 code units (Java characters)** ([#1206](https://github.com/nisshi-io/solace-nisshi/pull/1206)). Such a partition answers `OFFSET_METADATA_TOO_LARGE`, and the request's other partitions are still stored, as with Kafka's default `offset.metadata.max.bytes`. The limit can't be changed, so an application that commits longer metadata must shorten it. Longer metadata that an earlier version stored is still returned until the group commits that partition again.
- **CreateTopics refuses a name that collides with an existing topic** ([#1186](https://github.com/nisshi-io/solace-nisshi/pull/1186)). Two names collide when they differ only in `.` and `_`. With `x.y` existing, a create of `x_y` answers `INVALID_TOPIC_EXCEPTION` with Kafka's message, `Topic 'x_y' collides with existing topic: x.y`. Topics that already collide stay as they are. An application that creates such a pair must rename one of them.
- **A producer that sets the `LogAppendTime` bit on a batch is refused in two more cases** ([#1240](https://github.com/nisshi-io/solace-nisshi/pull/1240)). Such a batch gets `INVALID_TIMESTAMP`, which clients don't retry, on a `LogAppendTime` topic, and on a `CreateTime` topic when its `max_timestamp` is -1. Kafka refuses the same batches. Producers that leave the bit clear see no change.
- **DescribeConfigs for a topic now lists every topic config** ([#1194](https://github.com/nisshi-io/solace-nisshi/pull/1194)). It returns all 36 Kafka topic configs, with `DEFAULT_CONFIG` and Kafka's default value for each config the topic doesn't set. A client that treats every entry as set on the topic, instead of filtering on `ConfigSource`, now sees about 36 more entries, and must filter on `ConfigSource`. A Kafka config the topic sets now has its Kafka type, for example `LONG` for `retention.ms`, instead of `STRING`; `nisshi.*` configs stay `STRING`. On memory, S3, Google Cloud Storage and `null://`, describing a topic that doesn't exist now fails with `UnknownTopicOrPartitionException`.
- **Storage failures now answer retriable or non-retriable error codes by cause** ([#1290](https://github.com/nisshi-io/solace-nisshi/pull/1290)). A permanent failure, such as a stored value that can't be decoded, answers `UNKNOWN_SERVER_ERROR`. Clients then report it instead of retrying until their timeout. A transient failure answers a code that clients retry. One case can stop a producer: a permanent storage failure in InitProducerId now answers `UNKNOWN_SERVER_ERROR`. Before, the broker closed the connection and the producer reconnected. See Changed.
- **SlateDB (deprecated): a consumer group that an earlier version stored with members doesn't decode after the upgrade** ([#1174](https://github.com/nisshi-io/solace-nisshi/pull/1174)). Its consumers can't join it, and it can't be described. SlateDB stores groups in a format that can't fill in the two new member fields. Delete and recreate affected groups, or stay on 0.8.1. Other engines read such groups, and show an empty client ID and host for each member until the member joins again.
- **Rollback.** There are no schema changes.
  - 0.8.1 rejects the new `--auto-create-topics-enable` and `--num-partitions` flags and won't start with them. If you may roll back, set these options through `AUTO_CREATE_TOPICS_ENABLE` and `NUM_PARTITIONS`, which 0.8.1 ignores ([#1203](https://github.com/nisshi-io/solace-nisshi/pull/1203)). 0.8.1 also doesn't accept `nisshi topic list --output` ([#1229](https://github.com/nisshi-io/solace-nisshi/pull/1229)).
  - Memory, S3 and Google Cloud Storage: 0.8.1 ignores, and drops when it next writes the document, the new `version` field of each time index ([#1198](https://github.com/nisshi-io/solace-nisshi/pull/1198)), the `producer_epochs` entry in `watermark.json` and the `epoch_starts` entry in `meta.json` ([#1218](https://github.com/nisshi-io/solace-nisshi/pull/1218)). Answers stay correct, but the producers those entries covered fall back to the older epoch checks until they bump their epoch through an upgraded broker. A 0.8.1 broker that shares a bucket with an upgraded one has the same effect. 0.8.1 doesn't check the sequence on a lake-sink topic, so a retry there can again be stored twice ([#1215](https://github.com/nisshi-io/solace-nisshi/pull/1215)).
  - PostgreSQL, SQLite, Turso, memory, S3 and Google Cloud Storage: 0.8.1 ignores each group member's stored client ID and host, and drops them when it next stores the group ([#1174](https://github.com/nisshi-io/solace-nisshi/pull/1174)).
  - Dashboards and alerts that you moved to the snake_case `operation` values stop matching after a rollback. Match both spellings ([#1264](https://github.com/nisshi-io/solace-nisshi/pull/1264)).
- **Library users.**
  - `Storage` has a new required method, `pending_txn_offsets(&self, group_id: &str) -> Result<BTreeSet<Topition>>`. A `Storage` implementation without transactions returns an empty set ([#1236](https://github.com/nisshi-io/solace-nisshi/pull/1236)). `Storage` also has `current_offset_stage`, which has a default body. A type that wraps a `Storage` must forward it, or a Fetch on memory, S3 or Google Cloud Storage can reset a consumer that is only ahead of a cached high watermark ([#1273](https://github.com/nisshi-io/solace-nisshi/pull/1273)).
  - `Storage::offset_fetch` and `Storage::committed_offset_topitions` return `BTreeMap<Topition, CommittedOffset>` instead of `BTreeMap<Topition, i64>`, and so do the matching `nisshi_storage::Response` variants. Return `CommittedOffset::uncommitted()` for a partition without a committed offset ([#1206](https://github.com/nisshi-io/solace-nisshi/pull/1206)).
  - `nisshi_storage::Request` and `Response` have new `PendingTxnOffsets` and `CurrentOffsetStage` variants ([#1236](https://github.com/nisshi-io/solace-nisshi/pull/1236), [#1273](https://github.com/nisshi-io/solace-nisshi/pull/1273)). `Request` no longer implements `Display`. Call `request.operation()` instead, which returns the new `nisshi_storage::StorageOperation` ([#1264](https://github.com/nisshi-io/solace-nisshi/pull/1264)).
  - `nisshi_storage::Error` has new variants, `nisshi_storage::Error::InvalidStorageOptionValue` ([#1185](https://github.com/nisshi-io/solace-nisshi/pull/1185)) and `UnexpectedLibSqlValue`, behind the `libsql` feature ([#1188](https://github.com/nisshi-io/solace-nisshi/pull/1188)). `parse_storage_option` is a new public function. The new methods `Error::is_transient` and `Error::error_code(retriable)` replace `group_request_error_code`. `RequestSender` and `RequestReceiver` now carry `Result<Response>`, so code that sends on the storage channel directly sends `Ok(response)` ([#1290](https://github.com/nisshi-io/solace-nisshi/pull/1290)).
  - A crate that builds `nisshi-storage-sql` with only one SQL feature no longer gets the other engines' `nisshi_storage::Error` variants and `From` impls, for example `Error::TokioPostgres` in a `libsql`-only build. If you match on one, turn on the matching `nisshi-storage` feature ([#1242](https://github.com/nisshi-io/solace-nisshi/pull/1242)).
  - `nisshi_broker::Error` has a new variant, `ListenerHostUnresolved` ([#1181](https://github.com/nisshi-io/solace-nisshi/pull/1181)).
  - `Coordinator::join` takes a new `client_host: Option<&str>` argument after `client_id`. `nisshi_storage::GroupMember` has two new public fields, `client_id` and `client_host`. `impl From<&GroupDetail> for consumer_group_describe_response::DescribedGroup` is removed. The broker inserts a new `nisshi_service::PeerAddressExtension` into each connection it accepts ([#1174](https://github.com/nisshi-io/solace-nisshi/pull/1174)). `Coordinator` has a new required method, `txn_offset_commit_fence` ([#1219](https://github.com/nisshi-io/solace-nisshi/pull/1219)).
  - `MetadataService` has new fields, `topic_creation: TopicCreationConfig` and `auto_create_refusals: AutoCreateRefusals`, and its `Service` impl requires `G: Storage + Clone`. `nisshi_broker::service::services`, `nisshi_broker::service::storage::services` and their `metadata` helpers take these values, and `create_topics` takes the `TopicCreationConfig`. Pass a clone of one `AutoCreateRefusals` to every connection. `CreateTopicsValidationLayer` is a struct with `new()` and `.num_partitions(n)`. `ValidatedCreateTopicsRequest::new(request, num_partitions)` replaces `TryFrom<CreateTopicsRequest>`. `Broker::builder()` has `.topic_creation(..)` ([#1203](https://github.com/nisshi-io/solace-nisshi/pull/1203), [#1238](https://github.com/nisshi-io/solace-nisshi/pull/1238)).
  - `DeleteRecordsService` now calls `Storage::delete_records` with one partition at a time, and treats an `Err` as that partition's answer ([#1265](https://github.com/nisshi-io/solace-nisshi/pull/1265)).
  - `nisshi_sans_io` has new error variants, `Error::OffsetDeltaOverflow` ([#1191](https://github.com/nisshi-io/solace-nisshi/pull/1191)) and `ErrorCode::TransactionAbortable` ([#1209](https://github.com/nisshi-io/solace-nisshi/pull/1209)). An exhaustive `match` must handle them.

### Added

- `--auto-create-topics-enable` (`AUTO_CREATE_TOPICS_ENABLE`) and `--num-partitions` (`NUM_PARTITIONS`) broker settings, as Kafka's `auto.create.topics.enable` and `num.partitions`. The broker logs each auto-created topic at `info`, and a storage failure while it auto-creates one at `warn` as `auto-creating topic failed` ([#1203](https://github.com/nisshi-io/solace-nisshi/pull/1203), [#1207](https://github.com/nisshi-io/solace-nisshi/pull/1207)).
- The `pool_max_size` option of a `postgres://` storage URL sets the size of the connection pool (default 16, from 2 to 262143). Fetch and ListOffsets each get half of the pool for reads. The broker logs the pool size and both read limits at startup. A value outside the range stops startup ([#1200](https://github.com/nisshi-io/solace-nisshi/pull/1200)).
- `nisshi topic list --output json` prints the topics of the broker's Metadata response as JSON, as earlier releases did, for scripts ([#1229](https://github.com/nisshi-io/solace-nisshi/pull/1229)).
- Metrics:
  - `nisshi_storage_maintenance_sweeps`, by `sweep`, `engine` and `outcome` (`ok` or `error`) ([#1279](https://github.com/nisshi-io/solace-nisshi/pull/1279)).
  - `nisshi_fetch_full_listing`, which counts each partition read of a Fetch on memory, S3 or Google Cloud Storage that falls back to listing the whole partition ([#1202](https://github.com/nisshi-io/solace-nisshi/pull/1202)).
  - `nisshi_fetch_ahead_of_cached_high_watermark` ([#1273](https://github.com/nisshi-io/solace-nisshi/pull/1273)).
  - A `limit` attribute (`connection` or `engine`) on `nisshi_storage_read_deadline_exceeded` misses with `stage` `queued` ([#1190](https://github.com/nisshi-io/solace-nisshi/pull/1190)).
  - The `not_started` stage on that counter, with `operation` `delete_records` ([#1265](https://github.com/nisshi-io/solace-nisshi/pull/1265)).
  - The `overlapped` outcome of `nisshi_objectstore_cache_entries` ([#1213](https://github.com/nisshi-io/solace-nisshi/pull/1213)).
  - In `nisshi proxy`, `batch_rejected`, by error code ([#1205](https://github.com/nisshi-io/solace-nisshi/pull/1205)), and `batch_bypassed` ([#1210](https://github.com/nisshi-io/solace-nisshi/pull/1210)).
- `docs/consumer-groups.md` explains how consumer groups and committed offsets work. It walks through a `kafka-consumer-groups` example and lists the limits of this release ([#1221](https://github.com/nisshi-io/solace-nisshi/pull/1221)).
- The documentation says which authentication mechanisms the broker accepts, which engines can store users, and how to create the first user ([#1193](https://github.com/nisshi-io/solace-nisshi/pull/1193)).

### Changed

- Storage failures are sorted into transient and permanent in one place. A permanent failure answers `UNKNOWN_SERVER_ERROR`, and the code an engine's own Kafka error carries is kept ([#1290](https://github.com/nisshi-io/solace-nisshi/pull/1290), [#1188](https://github.com/nisshi-io/solace-nisshi/pull/1188)). Each API answers a transient failure with a code its clients retry:
  - OffsetFetch, ListGroups and DescribeGroups answer `COORDINATOR_NOT_AVAILABLE`. These APIs used to answer it for almost every storage failure, so a client kept retrying a failure that can't clear.
  - Produce, ListOffsets, DeleteRecords and DescribeConfigs answer `KAFKA_STORAGE_ERROR`. Produce used to answer `UNKNOWN_SERVER_ERROR`, so a short database or object store outage failed the batch at once. On memory, S3 and Google Cloud Storage, a failed record write or sequence advance of an idempotent batch still answers `UNKNOWN_SERVER_ERROR`, because the batch may have been stored.
  - InitProducerId answers `COORDINATOR_LOAD_IN_PROGRESS`. It used to close the connection, or answer `UNKNOWN_SERVER_ERROR` when a SQL engine's commit failed.
  - CreateTopics answers `NOT_CONTROLLER`. A topic that fails in a response where another topic succeeded answers `UNKNOWN_SERVER_ERROR`, because the Java admin client sends the whole request again on `NOT_CONTROLLER`.
  - IncrementalAlterConfigs answers `REQUEST_TIMED_OUT`.
  - DescribeConfigs answers each resource on its own, so one resource whose read fails no longer fails the whole request.
  - In libSQL's `mode=mpsc`, a panicked storage task answers `UNKNOWN_SERVER_ERROR` instead of a retriable code.
  - On SQLite, Turso and SlateDB, every engine error still counts as transient.
- DescribeConfigs for a topic lists every Kafka topic config, with `DEFAULT_CONFIG` for each one the topic doesn't set, and returns only the requested keys. A config the topic sets has its Kafka type. `kafka-configs --describe --all` now prints the defaults ([#1194](https://github.com/nisshi-io/solace-nisshi/pull/1194)).
- CreateTopics refuses a name that differs from an existing topic's only in `.` and `_`, with `INVALID_TOPIC_EXCEPTION`, also under `validate_only` ([#1186](https://github.com/nisshi-io/solace-nisshi/pull/1186)).
- Metadata auto-creation goes through CreateTopics, so auto-created topics get the same checks and use `--num-partitions`. A request is capped at 10,000 partitions in total ([#1203](https://github.com/nisshi-io/solace-nisshi/pull/1203), [#1238](https://github.com/nisshi-io/solace-nisshi/pull/1238)).
- A Fetch above the high watermark answers `OFFSET_OUT_OF_RANGE`, as Kafka does above the log end offset. `nisshi_fetch_offset_out_of_bounds` counts it with `bound` set to `above_high_watermark`, once per Fetch ([#1273](https://github.com/nisshi-io/solace-nisshi/pull/1273)).
- Produce refuses `acks` outside `-1`, `0` and `1` with `INVALID_REQUIRED_ACKS` ([#1192](https://github.com/nisshi-io/solace-nisshi/pull/1192)). It also refuses a batch marked `LogAppendTime` on a `LogAppendTime` topic, or with a `max_timestamp` of -1, with `INVALID_TIMESTAMP` and Kafka's message ([#1240](https://github.com/nisshi-io/solace-nisshi/pull/1240)).
- OffsetFetch answers `""` for a null commit metadata at every version, as Kafka does. Versions 8 and later answered `null` before ([#1206](https://github.com/nisshi-io/solace-nisshi/pull/1206)).
- A storage URL option for S3, Google Cloud Storage or SQLite whose value doesn't parse stops startup instead of falling back to its default ([#1185](https://github.com/nisshi-io/solace-nisshi/pull/1185)).
- On PostgreSQL, each client connection gets a share of the Fetch and ListOffsets reads: at most 2 Fetch reads and 4 ListOffsets reads in flight, or the whole limit when the pool is smaller. A read that a connection abandoned after its deadline now holds back that connection's next request, not every connection. As a result, a connection with slow partitions can get partitions back with no records until its own statements end ([#1190](https://github.com/nisshi-io/solace-nisshi/pull/1190)). `nisshi proxy` in front of a PostgreSQL broker is not a production setup, because the proxy spreads one client's reads over many origin connections ([#1281](https://github.com/nisshi-io/solace-nisshi/pull/1281)).
- On PostgreSQL, produces to different partitions run concurrently. Before, a produce locked the cluster's and the topic's rows, so the broker wrote one produce at a time, whatever the number of partitions ([#1175](https://github.com/nisshi-io/solace-nisshi/pull/1175)).
- On PostgreSQL, the `retention.bytes` sweep reads only about as many records as each capped partition may keep, instead of every record. The same records are deleted as before ([#1054](https://github.com/nisshi-io/solace-nisshi/pull/1054)).
- On libSQL and Turso, DeleteRecords commits each partition on its own, as PostgreSQL and Kafka do. A failure part way through a request no longer rolls back the partitions before it. A partition whose call hasn't started 5 s after the request arrived answers `REQUEST_TIMED_OUT`, on every engine ([#1265](https://github.com/nisshi-io/solace-nisshi/pull/1265)).
- A Fetch reads existing records up to the request's byte limits, instead of stopping after about `max_wait`. On slow storage, a read can take up to its share of the `max_wait` + 5 s fetch deadline, and returns more data ([#1231](https://github.com/nisshi-io/solace-nisshi/pull/1231)).
- A failed storage maintenance sweep (`maintain` or `maintain_transactions`) is logged at `warn` instead of `debug`. The line names the engine, the error and what stops working, such as retention, compaction, the lake sink or transaction timeouts. The broker logs at most one line per sweep every 5 minutes, and a line when the sweep recovers ([#1279](https://github.com/nisshi-io/solace-nisshi/pull/1279)).
- `nisshi broker` prints its startup banner only once its listener is bound. A broker that fails to start prints only its `error:` line. A broker that is still connecting to slow storage shows nothing on stdout until it connects, and the storage connection progress line appears above the banner ([#1235](https://github.com/nisshi-io/solace-nisshi/pull/1235)).
- `nisshi --help` and each tool's `--help` now say that `cat`, `generator`, `perf`, `topic`, `user` and `proxy` are for development and demos, and that the client tools connect in plaintext only. A failed `nisshi user create` prints its error on a line that starts with `error: `, like the other commands ([#1227](https://github.com/nisshi-io/solace-nisshi/pull/1227)).
- A `nisshi` built without the `iceberg`, `delta` or `parquet` feature names the missing feature and how to install it when you run that lake subcommand. Before, it printed clap's `unexpected argument` or `unrecognized subcommand` error ([#1228](https://github.com/nisshi-io/solace-nisshi/pull/1228)).
- Building `nisshi` with only one of the `libsql`, `postgres` or `turso` features no longer compiles the other SQL clients ([#1242](https://github.com/nisshi-io/solace-nisshi/pull/1242)).
- The README is shorter, and its reference sections moved to `docs/install.md`, `docs/storage.md`, `docs/commands.md`, `docs/security.md` and `docs/metrics.md`. A new `ARCHITECTURE.md` describes the code for contributors. The Kafka CLI client configurations (`command*.properties`) and JAAS samples moved from the repository root to `etc/kafka-client/` ([#1225](https://github.com/nisshi-io/solace-nisshi/pull/1225)).

### Fixed

- `kafka-consumer-groups --describe` shows each member's consumer ID, host and client ID, and `--describe --members` lists the members. Before, the Kafka 3.8 and later tools printed no members on every engine ([#1174](https://github.com/nisshi-io/solace-nisshi/pull/1174)):
  - ConsumerGroupDescribe answers `GROUP_ID_NOT_FOUND` with "Group <id> is not a consumer group." for a stored classic group, so the admin client falls back to DescribeGroups, as with Kafka.
  - DescribeGroups reports each member's group instance ID, client ID and host. For a `Stable` group, it also reports each member's subscription and assignment, and the group's protocol.
- DescribeGroups for a group that doesn't exist answers `NONE` and the state `Dead`, as Kafka does at versions 0 to 5. `kafka-consumer-groups --describe` then says the group doesn't exist, instead of failing with `GroupIdNotFoundException` ([#1216](https://github.com/nisshi-io/solace-nisshi/pull/1216)).
- OffsetFetch returns the committed leader epoch and metadata on every engine except SlateDB. Before, it answered leader epoch `-1` and empty metadata, so an application that keeps state in its commit metadata got nothing back ([#1206](https://github.com/nisshi-io/solace-nisshi/pull/1206)).
- On every engine except SlateDB, an idempotent Java producer that sends a batch at an older epoch than its partition's now gets `INVALID_PRODUCER_EPOCH`, bumps its epoch and continues, as with Kafka. Before, it got `PRODUCER_FENCED`, and that send and every later one failed. A bump to epoch 32766 or above is still refused, now with `INVALID_PRODUCER_EPOCH`, so the Java producer moves to a new producer ID. A batch from a retired producer ID still gets `PRODUCER_FENCED` ([#1223](https://github.com/nisshi-io/solace-nisshi/pull/1223)).
- An idempotent producer's records are no longer stored twice when two of its batches to one partition race:
  - On PostgreSQL, a retry of a batch that is still in flight is stored once, and the other attempt gets `DUPLICATE_SEQUENCE_NUMBER`. A batch at an older epoch that is in flight during an epoch bump is stored before the newer batch, or refused. The check now runs under the partition's lock, so idempotent produces to one partition hold that lock a few round trips longer, which lowers throughput when many idempotent producers write to one partition ([#1204](https://github.com/nisshi-io/solace-nisshi/pull/1204)).
  - On memory, S3 and Google Cloud Storage, a batch at an older epoch that gets its offset after the epoch bump is refused with `INVALID_PRODUCER_EPOCH` before it is stored. The partition remembers the newest epoch of up to 1024 producers that have bumped their epoch ([#1218](https://github.com/nisshi-io/solace-nisshi/pull/1218)).
  - On memory, S3 and Google Cloud Storage, a produce to a `nisshi.lake.sink` topic checks the producer sequence. A retry gets the first attempt's offset and doesn't write its rows to the lake a second time. A batch that skips sequence numbers gets `OUT_OF_ORDER_SEQUENCE_NUMBER` ([#1215](https://github.com/nisshi-io/solace-nisshi/pull/1215)).
- On memory, S3 and Google Cloud Storage, a read of `meta.json` or a partition's `watermark.json` that overlapped a write could cache the older version. Readers then saw stale data until the next write or for up to 5 s: for example, a new idempotent producer got `UNKNOWN_PRODUCER_ID`, or an acknowledged produce was missing from `ListOffsets(Latest)` ([#1213](https://github.com/nisshi-io/solace-nisshi/pull/1213)).
- A consumer with `fetch.max.wait.ms=0` (`fetch.wait.max.ms=0` in librdkafka) receives records. Before, a Fetch with `max_wait` 0 answered with no partitions on every engine ([#1231](https://github.com/nisshi-io/solace-nisshi/pull/1231)).
- A Fetch whose `min_bytes` isn't met waits for records as Kafka does. Before, a long wait could return no records although the partition held some, and a wait could end early with less than `min_bytes`. The wait now ends as soon as the bytes reach `min_bytes`, and `min_bytes` is capped at `max_bytes`. This affects only consumers that set `fetch.min.bytes` above 1 ([#1199](https://github.com/nisshi-io/solace-nisshi/pull/1199)).
- On memory, S3 and Google Cloud Storage, a Fetch lists only the batches near the fetch offset instead of the whole partition, so its cost no longer grows with the partition. A consumer no longer gets stuck when listing the partition takes longer than `max_wait`. A batch deleted between the listing and its read is skipped. On Google Cloud Storage, the broker now passes start-after listings to the store, which also helps ListOffsets by timestamp. A store that doesn't list keys in order, such as an S3 Express One Zone directory bucket, still lists the whole partition ([#1202](https://github.com/nisshi-io/solace-nisshi/pull/1202)).
- On S3 and Google Cloud Storage, a lookup by timestamp (`offsetsForTimes`) no longer answers no match for a record that exists. The time index of a batch stored before 0.7.0 was built from the timestamp in the batch header, which the client wrote. The index is now built from the records, and an index built from headers is rebuilt ([#1198](https://github.com/nisshi-io/solace-nisshi/pull/1198)).
- A storage error in one partition of ListOffsets, in one partition of DeleteRecords on every engine except PostgreSQL (which already did), or in one group of DescribeGroups on PostgreSQL and SQLite, no longer fails the whole request and closes the connection. That partition or group answers its own error, and the others still get their answers. A timestamp lookup on memory, S3 or Google Cloud Storage that hits a transient object store failure answers `KAFKA_STORAGE_ERROR`, which the admin client retries, instead of `UNKNOWN_SERVER_ERROR` ([#1201](https://github.com/nisshi-io/solace-nisshi/pull/1201), [#1211](https://github.com/nisshi-io/solace-nisshi/pull/1211), [#1265](https://github.com/nisshi-io/solace-nisshi/pull/1265), [#1195](https://github.com/nisshi-io/solace-nisshi/pull/1195)).
- On memory, S3 and Google Cloud Storage, OffsetCommit for a partition index that the topic doesn't have answers `UNKNOWN_TOPIC_OR_PARTITION` and stores nothing. Before, it stored an offset that OffsetFetch then returned ([#1184](https://github.com/nisshi-io/solace-nisshi/pull/1184)).
- On SQLite, ListOffsets and Fetch work on a partition that holds a record with no timestamp (-1). Before, both failed with a storage error that clients retried forever ([#1294](https://github.com/nisshi-io/solace-nisshi/pull/1294)).
- The Turso engine (`turso://`, alpha) creates all of its tables at startup, and a failed DDL statement now stops startup. Before, it started without its topic, producer and consumer group tables. Any SQL error no longer panics, a duplicate CreateTopics answers `TOPIC_ALREADY_EXISTS`, and timestamps are stored as on libSQL ([#1255](https://github.com/nisshi-io/solace-nisshi/pull/1255), [#1188](https://github.com/nisshi-io/solace-nisshi/pull/1188)).
- On PostgreSQL, a maintenance pass runs every step even when an earlier step fails. Before, a failed retention sweep skipped the removal of records below the log start, compaction and the lake. Each failed step logs at `warn` ([#1266](https://github.com/nisshi-io/solace-nisshi/pull/1266)).
- A storage URL that sets `maintenance_interval` or `transaction_maintenance_interval` keeps its other options as written, such as `options=-c%20statement_timeout%3D5000`. Before, the broker rewrote `%20` as `+`, which PostgreSQL reads literally ([#1212](https://github.com/nisshi-io/solace-nisshi/pull/1212)).
- On a topic with a schema and an Iceberg lake, two produces that race to create the topic's namespace or table no longer fail. The one that loses the race uses what the other created ([#1175](https://github.com/nisshi-io/solace-nisshi/pull/1175)).
- With produce batching (`batch_max_delay`) on S3 and Google Cloud Storage, a valid request no longer fails because of the batches merged with it ([#1191](https://github.com/nisshi-io/solace-nisshi/pull/1191), [#1262](https://github.com/nisshi-io/solace-nisshi/pull/1262)):
  - A merge whose decoded size would go over 100 MiB is split into several writes. Before, every producer in the flush got `MESSAGE_TOO_LARGE`, or the broker stored a batch that Nisshi couldn't decode.
  - A storage error fails only the producers whose batches were in the failed write.
  - A record whose offset delta overflows the merge no longer gets wrong offsets. The broker writes each batch as sent instead.
- `nisshi proxy` on a `nisshi.batch=true` topic fails only the request whose batch can't be merged with that partition's other queued requests. Before, the proxy forwarded the partition with no batches or failed it for every request, and a debug build could panic. Such a request gets `INVALID_RECORD`, or `MESSAGE_TOO_LARGE` when the batch is over the decoded size limit. The proxy refuses a request that sends two batches for one partition, as Kafka does ([#1191](https://github.com/nisshi-io/solace-nisshi/pull/1191), [#1205](https://github.com/nisshi-io/solace-nisshi/pull/1205), [#1254](https://github.com/nisshi-io/solace-nisshi/pull/1254)).
- `nisshi proxy` on a `nisshi.batch=true` topic no longer merges batches from two idempotent producers into one batch with the first producer's ID, which made both producers fail with `OUT_OF_ORDER_SEQUENCE_NUMBER`. It no longer pulls other clients' records into a transactional request either ([#1210](https://github.com/nisshi-io/solace-nisshi/pull/1210)).
- A Metadata v10 or v11 request that names a topic by ID, or leaves the name null, gets `INVALID_REQUEST` from the broker and from `nisshi proxy`, as from Kafka. Before, the response frame couldn't be decoded ([#1293](https://github.com/nisshi-io/solace-nisshi/pull/1293)).
- Transactions are still refused at InitProducerId, so clients don't reach these fixes yet ([#1208](https://github.com/nisshi-io/solace-nisshi/pull/1208), [#1209](https://github.com/nisshi-io/solace-nisshi/pull/1209), [#1219](https://github.com/nisshi-io/solace-nisshi/pull/1219), [#1236](https://github.com/nisshi-io/solace-nisshi/pull/1236), [#1244](https://github.com/nisshi-io/solace-nisshi/pull/1244)):
  - A Produce whose `transactional_id` is unknown, or whose transactional batch goes to a partition not added to the transaction, is refused before anything is stored, with `INVALID_PRODUCER_ID_MAPPING`, `TRANSACTION_ABORTABLE` or `CONCURRENT_TRANSACTIONS`, as Kafka does. Produce v10 and older get `INVALID_TXN_STATE` instead of `TRANSACTION_ABORTABLE`.
  - TxnOffsetCommit is checked against the group's member, generation and group instance ID.
  - OffsetFetch with `require_stable` answers `UNSTABLE_OFFSET_COMMIT` while a transaction holds the offset.
  - On memory, S3 and Google Cloud Storage, an open transaction is recorded before the high watermark rises.
  - On PostgreSQL, SQLite and Turso, Fetch never answers a last stable offset below the log start.
- `nisshi cat consume`:
  - It starts at `--fetch-offset` and sends `--partition-max-bytes`. Before, it always read from the start of the partition ([#1234](https://github.com/nisshi-io/solace-nisshi/pull/1234)).
  - It reports a partition error and exits non-zero. A missing topic prints, for example, `looking up topic "no-such-topic" failed: UnknownTopicOrPartition (3)`, instead of printing nothing or a debug dump ([#1234](https://github.com/nisshi-io/solace-nisshi/pull/1234), [#1272](https://github.com/nisshi-io/solace-nisshi/pull/1272)).
  - It no longer prints a transaction marker as a record ([#1272](https://github.com/nisshi-io/solace-nisshi/pull/1272)).
- `nisshi cat produce` and `nisshi cat consume` no longer panic when given `--schema-registry`, or when `SCHEMA_REGISTRY` is set in the environment. `${VAR}` in `cat`'s `--schema-registry` is now expanded, as it is for the broker ([#1291](https://github.com/nisshi-io/solace-nisshi/pull/1291)).
- An invalid URL option, such as `nisshi broker --schema-registry foo`, prints `invalid URL: relative URL without a base` instead of `Url(RelativeUrlWithoutBase)` ([#1292](https://github.com/nisshi-io/solace-nisshi/pull/1292)).

### Security

- The release binaries and image now use `thrift` 0.23.0, through `parquet` 58.4.1, instead of `thrift` 0.17.0, which [RUSTSEC-2026-0435](https://rustsec.org/advisories/RUSTSEC-2026-0435.html) affects: an unbounded allocation in `TBinaryInputProtocol::read_bytes` and `read_string`. Nisshi doesn't use thrift's binary protocol, so we don't know of a way to reach the flaw in earlier releases ([#1271](https://github.com/nisshi-io/solace-nisshi/pull/1271)).
- On a topic with an Avro schema, the broker refuses a record key or value whose object container uses a codec other than `null`, before it decompresses anything. Before, a few compressed bytes could expand to gigabytes in memory before validation. See Upgrade notes ([#1182](https://github.com/nisshi-io/solace-nisshi/pull/1182)).
- A client that sent a new group ID in each Heartbeat, LeaveGroup, SyncGroup or rejected JoinGroup grew the group coordinator's in-memory caches until the broker restarted. The broker now caches only groups that storage holds, and frees a group's wake-up signal when its join or sync ends ([#1232](https://github.com/nisshi-io/solace-nisshi/pull/1232)).
- One Metadata request can no longer auto-create an unbounded number of topics. Auto-creation is capped at 10,000 partitions per request, as in Kafka ([#1203](https://github.com/nisshi-io/solace-nisshi/pull/1203)).
- A `--listener-url` with a host name no longer listens on every interface. See Upgrade notes ([#1181](https://github.com/nisshi-io/solace-nisshi/pull/1181)).

## [0.8.1] - 2026-10-27

### Upgrade notes

- **Topics set to `message.timestamp.type=LogAppendTime` now get the broker's timestamps** ([#1059](https://github.com/nisshi-io/nisshi/pull/1059)). Earlier versions ignored the setting, so records kept the producer's timestamps. After the upgrade, each new record on such a topic carries the time the broker stored it, so the log switches from producer time to broker time at the upgrade. Records stored before the upgrade keep their timestamps. From then on, timestamp lookups (`offsetsForTimes`, `kafka-consumer-groups --reset-offsets --to-datetime`) and lake tables use the broker's time for these topics. Before you upgrade, find the affected topics with `kafka-configs --describe --entity-type topics --entity-name <topic>`.
- **`message.timestamp.type` must be exactly `CreateTime` or `LogAppendTime`** ([#1059](https://github.com/nisshi-io/nisshi/pull/1059)). CreateTopics and IncrementalAlterConfigs now refuse any other value with `INVALID_CONFIG` and Kafka's message. The match is case-sensitive, and white space around the value is ignored. Earlier versions stored any value. A stored value that is neither of the two, such as `logappendtime`, is read as `CreateTime`, so its topic keeps producer timestamps. Set the value again with the exact name, for example `kafka-configs --alter --entity-type topics --entity-name <topic> --add-config message.timestamp.type=LogAppendTime`.
- **A batch that the producer marks `LogAppendTime` gets the same checks as any other batch** ([#1059](https://github.com/nisshi-io/nisshi/pull/1059)). On a `CreateTime` topic, its timestamps must fall within the timestamp window, or it gets `INVALID_TIMESTAMP`. On every engine and topic, its records must decode, or it gets `INVALID_RECORD`. Before, the bit skipped the window, and on memory, S3, Google Cloud Storage and SlateDB it also skipped decoding unless a schema registry or lake was configured. Producers that leave the bit unset see no change.
- **Memory, S3 and Google Cloud Storage: an idempotent batch that reuses a sequence number now fails instead of being acknowledged and lost** ([#1167](https://github.com/nisshi-io/nisshi/pull/1167)). Such a batch neither starts at the producer's next sequence nor repeats one of its last 5 batches, and it now gets `OUT_OF_ORDER_SEQUENCE_NUMBER`. librdkafka treats this as a fatal error, and the application must recreate the producer. Before, the broker answered `DUPLICATE_SEQUENCE_NUMBER`, which clients count as delivered, and stored nothing. If you see this error after the upgrade, a client resent a sequence number it had already used. The broker logs each one at `warn`, and `nisshi_produce_idempotent_sequence_check` counts it with `outcome` set to `out_of_order`. The new rule starts on each partition at the producer's first write through an upgraded broker, so a batch that was in flight across the restart is still accepted as a retry.
- **S3 and Google Cloud Storage with produce batching (`batch_max_delay`): idempotent producers' batches are no longer merged** ([#1167](https://github.com/nisshi-io/nisshi/pull/1167)). Each batch is written as its own object, so the broker writes more objects and makes more object store requests. Idempotence is the Java producer's default, so expect this for most Java clients. A queue that holds any idempotent batch is written one batch at a time; a queue that holds only non-idempotent batches is still merged.
- **Container image: three emSign root certificates are no longer trusted** ([#1162](https://github.com/nisshi-io/nisshi/pull/1162)). In the image, an outbound TLS connection fails with an unknown issuer error when the server's certificate chain ends at emSign ECC Root CA - G3, emSign Root CA - C1 or emSign ECC Root CA - C3. This covers connections to PostgreSQL, S3, Google Cloud Storage, Iceberg, Delta, OTLP and JSON Schema `$ref`. If a server you use has such a chain, reissue its certificate under another CA. Until then, mount a PEM bundle that holds that root and the public CAs the broker needs, and set `SSL_CERT_FILE` to it (it replaces the image's CA bundle rather than adding to it), or stay on the 0.8.0 image. See Security.
- **The broker warns at startup when certificate checks on object store connections are turned off** ([#1163](https://github.com/nisshi-io/nisshi/pull/1163)). It logs one warning for each of `AWS_ALLOW_INVALID_CERTIFICATES`, `GOOGLE_ALLOW_INVALID_CERTIFICATES`, `AZURE_ALLOW_INVALID_CERTIFICATES` and `ALLOW_INVALID_CERTIFICATES` that is set to `1`, `true`, `on`, `yes` or `y`. Names and values match in any case. The broker still starts. To clear the warning, unset the variable and trust the server's CA with `SSL_CERT_FILE` or `SSL_CERT_DIR`, as the README's "Outbound TLS" section describes.
- **Rollback.** There are no schema changes.
  - PostgreSQL, SQLite and Turso: don't roll back while you have a `LogAppendTime` topic. 0.8.0 serves each record stored with `LogAppendTime` with the time of the fetch as its timestamp. The stored rows keep the broker's time, so upgrading again fixes it ([#1059](https://github.com/nisshi-io/nisshi/pull/1059)).
  - Memory, S3 and Google Cloud Storage: 0.8.0 ignores the new `batches` entry of each producer in `meta.json` and drops it the next time it writes the file. Each partition then uses the old sequence answer until the producer writes to it again through an upgraded broker. A 0.8.0 broker that shares a bucket with an upgraded one has the same effect ([#1167](https://github.com/nisshi-io/nisshi/pull/1167)).
  - Every engine except SlateDB: a producer that bumped its epoch on some partitions under 0.8.1 can get `PRODUCER_FENCED` after a rollback, because 0.8.0 compares every batch with the producer's newest epoch. Restart such producers after rolling back ([#1168](https://github.com/nisshi-io/nisshi/pull/1168)).
  - The 0.8.0 image trusts the three emSign roots again ([#1162](https://github.com/nisshi-io/nisshi/pull/1162)).
- **Library users.**
  - `nisshi_sans_io::record::deflated::Batch::set_timestamps` takes a `TimestampType` before the two timestamps, and sets the batch's timestamp type ([#1059](https://github.com/nisshi-io/nisshi/pull/1059)).
  - The produce service calls `Storage::describe_config` for each topic of each Produce request, with the single key `message.timestamp.type`. If that call returns an error, or a result whose error code is neither `NONE` nor `UNKNOWN_TOPIC_OR_PARTITION`, every partition of the topic gets `UNKNOWN_SERVER_ERROR` ([#1059](https://github.com/nisshi-io/nisshi/pull/1059)).
  - `Storage::fetch` must return the first batch at the fetch offset even when that batch alone is larger than `max_bytes`. Otherwise a consumer whose limit is below that size never gets past it. The fetch service now counts each partition's returned bytes against the request's `max_bytes` ([#1161](https://github.com/nisshi-io/nisshi/pull/1161)).

The `outcome` values are `append`, `duplicate`, `out_of_order` and `duplicate_without_remembered_batches` ([#1167](https://github.com/nisshi-io/nisshi/pull/1167)).
- The README has a new "Outbound TLS" section. It covers which connections the broker opens and where their trusted CAs come from, how to trust a private CA with `SSL_CERT_FILE` or `SSL_CERT_DIR`, and why a `postgres://` storage URL should set `sslmode=require` ([#1163](https://github.com/nisshi-io/nisshi/pull/1163)).
- `docs/compatibility.md` compares the PostgreSQL, SQLite, in-memory and S3 engines. The README's storage table links to it ([#1134](https://github.com/nisshi-io/nisshi/pull/1134)).

### Changed

- The topic's `message.timestamp.type` sets each batch's timestamp type, as in Kafka; the producer's bit on the batch no longer does. On a `CreateTime` topic, a batch that the producer marks `LogAppendTime` is now stored as `CreateTime` with the producer's timestamps. 0.8.0 stored it with the broker's time ([#1059](https://github.com/nisshi-io/nisshi/pull/1059)).
- Produce reads each topic's `message.timestamp.type` once per request. On PostgreSQL, SQLite and Turso this adds a config lookup per topic. On memory, S3 and Google Cloud Storage, the lookup replaces a second metadata read that each partition's write made before ([#1059](https://github.com/nisshi-io/nisshi/pull/1059)).
- On PostgreSQL, DescribeConfigs with named config keys returns only those keys, as Kafka does. Before, it returned every config of the topic ([#1059](https://github.com/nisshi-io/nisshi/pull/1059)).
- An ApiVersions request above v4 still gets a v0 reply with `UNSUPPORTED_VERSION`. The reply now lists only the ApiVersions entry, versions 0 to 4, as Kafka does; before, it listed every API. franz-go v1.22.2, which the compatibility suite now runs, sends ApiVersions v5, and now retries at v4 on the same connection, as it does against Kafka. `nisshi proxy` answers with its own ApiVersions range instead of the origin's ([#1157](https://github.com/nisshi-io/nisshi/pull/1157)).
- With produce batching on S3 and Google Cloud Storage, the broker writes an idempotent producer's queued batches one at a time. It stores each batch with the sequence numbers the producer sent, so it can recognise a retry of that batch ([#1167](https://github.com/nisshi-io/nisshi/pull/1167)).

### Fixed

- Topics set to `message.timestamp.type=LogAppendTime` get the broker's time, as in Kafka ([#1059](https://github.com/nisshi-io/nisshi/pull/1059)):
  - Each record's timestamp is the time the broker stored its batch, and the Produce response returns that time in `log_append_time_ms` (it was always -1).
  - Timestamp lookups find records by that time on every engine except SlateDB. SlateDB still uses the producer's time.
  - Lake tables use that time in their timestamp column and date partition.
  - With produce batching on S3 and Google Cloud Storage, the broker no longer merges batches that it stamped at different times. Each record keeps the time that its own Produce response returned.
- On PostgreSQL, SQLite and Turso, each fetched batch's `max_timestamp` is the largest timestamp of its records. Before, it was the time of the fetch ([#1059](https://github.com/nisshi-io/nisshi/pull/1059)).
- On memory, S3 and Google Cloud Storage, DescribeConfigs no longer panics when it fails to read the topic's metadata. It returns an error instead ([#1059](https://github.com/nisshi-io/nisshi/pull/1059)).
- An idempotent producer can bump its own epoch after an error, as in Kafka ([KIP-360](https://cwiki.apache.org/confluence/display/KAFKA/KIP-360%3A+Improve+reliability+of+idempotent%2Ftransactional+producer)). In a bump, the producer keeps its producer ID, adds one to its epoch and restarts its sequence at 0. Before, memory, S3 and Google Cloud Storage answered the bumped batch with `PRODUCER_FENCED`, and PostgreSQL, SQLite and Turso with `UNKNOWN_SERVER_ERROR`. Clients treat `PRODUCER_FENCED` as fatal, so a transient error such as a timeout stopped the producer. Every engine except SlateDB now tracks the epoch per partition, as Kafka does ([#1168](https://github.com/nisshi-io/nisshi/pull/1168)):
  - A batch at a higher epoch than its partition's, at sequence 0, is stored. At any other sequence, it gets `OUT_OF_ORDER_SEQUENCE_NUMBER`.
  - A batch at the previous epoch is stored on a partition that hasn't seen the bump yet. The Java client sends such a retry after it bumps the epoch for another partition.
  - A batch at an epoch below its partition's still gets `PRODUCER_FENCED`, where Kafka answers `INVALID_PRODUCER_EPOCH`. A bump to epoch 32766 or above also gets `PRODUCER_FENCED`, which Kafka accepts.
- On memory, S3 and Google Cloud Storage, a batch that reused an idempotent producer's sequence number was acknowledged and never stored. The broker now remembers each producer's last 5 batches per partition, as Kafka does ([#1167](https://github.com/nisshi-io/nisshi/pull/1167)):
  - A batch with the same first and last sequence as a remembered batch is a retry. The broker answers it with no error and the base offset of the stored batch, and stores nothing. Before, a retry got `DUPLICATE_SEQUENCE_NUMBER` with base offset -1.
  - Any other batch that doesn't start at the next sequence gets `OUT_OF_ORDER_SEQUENCE_NUMBER`.
  - PostgreSQL, SQLite and Turso still answer every batch below the next sequence with `DUPLICATE_SEQUENCE_NUMBER` and don't store it. `docs/compatibility.md` describes this difference.
- On PostgreSQL, SQLite and Turso, a consumer no longer stalls on a record larger than its fetch limit. A Fetch whose `max_bytes` was below the size of the first record at the fetch offset returned no records. Now it returns that record ([#1161](https://github.com/nisshi-io/nisshi/pull/1161)):
  - On every engine, each partition's returned bytes now count against the request's `max_bytes`. Before, a request that listed many partitions, each starting with a large record, could get one large record for every partition.
  - Any partition can exceed its `partition_max_bytes` by one batch. Kafka allows this only for the first non-empty partition of a response.

### Security

- The container image no longer trusts emSign ECC Root CA - G3, emSign Root CA - C1 and emSign ECC Root CA - C3 ([#1162](https://github.com/nisshi-io/nisshi/pull/1162)). The eMudhra intermediate certificates whose private keys are compromised (CVE-2026-111943) chain to emSign ECC Root CA - G3. NSS 3.131.1 removed it, along with the retired emSign Root CA - C1 and emSign ECC Root CA - C3. emSign Root CA - G1 stays trusted, as in NSS. The image's base moves from `alpine:3.24.2` to `alpine:3.24.3`, whose `ca-certificates-bundle` 20261020 drops the three roots. The 0.8.0 image still trusted them, but its certificate verification (rustls-webpki 0.103.16 for [RUSTSEC-2026-0382](https://rustsec.org/advisories/RUSTSEC-2026-0382.html), [#1048](https://github.com/nisshi-io/nisshi/pull/1048)) already rejected any chain through the compromised intermediates. 0.7.0 and earlier, on Linux and in the image, have neither protection; upgrade.

## [0.8.0] - 2026-10-27

### Upgrade notes

- **PostgreSQL and SQLite: retention now deletes records that earlier versions kept, and the deletion can't be undone** ([#1021](https://github.com/nisshi-io/nisshi/pull/1021)). A topic without a `cleanup.policy` now has Kafka's default policy, `delete`. At the first maintenance run after the upgrade, such a topic loses its records older than its `retention.ms`. If it doesn't set `retention.ms` either, it loses every record older than 7 days. A topic that sets `retention.bytes` without a `cleanup.policy` is trimmed to that size. The affected topics are the ones whose `kafka-configs --describe` output doesn't list `cleanup.policy`. To keep every record of such a topic, set `retention.ms=-1` and remove `retention.bytes` before you upgrade. Don't use `cleanup.policy=compact` for this, because compaction keeps only the newest record of each key. Set `retention.ms=-1` only on topics without a `cleanup.policy`: on a topic whose policy contains `delete`, 0.7.0 deletes every record. The same applies after a rollback to 0.7.0. The first run can be expensive. On PostgreSQL it deletes the whole backlog in one statement and one transaction, with no statement timeout, so expect a spike in WAL and replication lag; if it fails, it rolls back and the next run starts over. On SQLite, each run reads the timestamp of every record of every topic without a policy, and holds the write lock while it does. SlateDB's retention is unchanged: it still skips a topic without a `cleanup.policy`, and `retention.ms=-1` still deletes every record. Because `APPEND compact` to an unset `cleanup.policy` now gives `delete,compact` (see Changed), that `APPEND` turns on deletion for a SlateDB topic.
- **Produce now enforces each topic's `max.message.bytes`, and a topic that doesn't set it gets Kafka's default of 1048588 bytes** ([#1090](https://github.com/nisshi-io/nisshi/pull/1090)). A producer that sends larger batches, for example with `max.request.size` or `batch.size` raised above 1 MiB, gets `RecordTooLargeException` after the upgrade. Raise the limit per topic, before or after upgrading, with `kafka-configs --alter --entity-type topics --entity-name <topic> --add-config max.message.bytes=<bytes>`. There is no broker-wide setting like Kafka's `message.max.bytes`, and `kafka-configs --describe` doesn't show the default for a topic that doesn't set the key. CreateTopics and IncrementalAlterConfigs now refuse a `max.message.bytes` they used to store, if it isn't an integer from 0 to 2147483647.
- **Transactional producers are refused** ([#1122](https://github.com/nisshi-io/nisshi/pull/1122)). InitProducerId with a `transactional.id` answers `TRANSACTIONAL_ID_AUTHORIZATION_FAILED`. A client that calls `initTransactions()` (Java) or `init_transactions()` (librdkafka) now fails at start-up with `TransactionalIdAuthorizationException`, and so does Kafka Streams with `processing.guarantee=exactly_once_v2`. A transactional producer that initialized before the upgrade fails at its next restart or its next aborted transaction. Restart transactional producers after upgrading so this happens at a time you choose. Idempotent producers (`enable.idempotence=true`, the Java default) are unaffected.
- **`--authentication` now stops the broker at startup on storage that can't store SCRAM users: `memory://`, `s3://`, `gs://`, `null://` and `turso://`** ([#1030](https://github.com/nisshi-io/nisshi/pull/1030)). On `memory://`, `s3://` and `gs://`, creating a SCRAM user used to report success and store nothing, so `--authentication` locked every client out; on `null://` it failed with an empty `UNSUPPORTED_SASL_MECHANISM`, and on `turso://` it panicked the connection. The error names the engine and the engines in the build that can store users. Move to PostgreSQL or SQLite, or start without `--authentication`.
- **ACL requests fail with `SECURITY_DISABLED`, as they do on Kafka without an authorizer** ([#1079](https://github.com/nisshi-io/nisshi/pull/1079)). `kafka-acls --list` used to succeed with no ACLs and now fails with `SecurityDisabledException`. Update scripts that expect it to succeed.
- **Topic configuration keys now start with `nisshi.`, and the `tansu.` keys keep working as deprecated aliases** ([#1125](https://github.com/nisshi-io/nisshi/pull/1125)). This replaces the 0.7.0 note that keys keep their `tansu.` prefix. Existing topics need no change. 0.7.0 and earlier read only `tansu.` keys: they store a `nisshi.` key, ignore it, and log no warning. To move a topic, first upgrade every broker and proxy. Then set the `nisshi.` key to the same value as the `tansu.` key, and keep both until you no longer need to roll back. Delete the `tansu.` key only after that. If a topic has only the `nisshi.` keys, a rollback to 0.7.0:
  - turns schema validation back on (PostgreSQL and libSQL);
  - stops virtual topics and proxy batching;
  - ignores the Delta partition and z-order keys;
  - makes every produce fail on a topic whose Delta table was created with `nisshi.lake.normalize` or `nisshi.lake.generate.*`;
  - with `nisshi.lake.sink=true`, stores records in the topic again, which leaves a gap for the offsets produced while the key applied.

  During a rolling upgrade, old and new brokers apply different settings to the same topic. With `nisshi.lake.sink=true`, new brokers write to the lake only and old brokers write to both the topic and the lake, so the topic has gaps.
- **The default log level is now `warn` (was `error`)** ([#1115](https://github.com/nisshi-io/nisshi/pull/1115)). With `RUST_LOG` unset or empty, the broker and every `nisshi` subcommand print warnings. Some warnings are logged per request or per connection, such as a failed TLS handshake, so a misbehaving client can now produce many lines. Set `RUST_LOG=error` to keep the old output.
- **Memory, S3 and Google Cloud Storage: ListOffsets `latest` jumps to the real end of the log** ([#1038](https://github.com/nisshi-io/nisshi/pull/1038)). On each partition that took a batch of more than one record, the end offset rises after the upgrade. Lag tools show the real lag, and a group that was reset `--to-latest` before the upgrade sits below the end and reads those records again.
- **Docker Compose: services listen on this computer only, and the broker depends on `db`** ([#1128](https://github.com/nisshi-io/nisshi/pull/1128)). Every service publishes its ports on `127.0.0.1`. To reach one from another computer, set `NISSHI_DB_PORTS`, `NISSHI_MINIO_PORTS` or `NISSHI_MINIO_CONSOLE_PORTS`, or change the port in a Compose override file. `docker compose up nisshi` now also starts `db` and waits until it is healthy, even when `.env` selects another storage engine. If `db` can't start, the broker doesn't start either; this happens when port 5432 is taken (set `NISSHI_DB_PORTS=127.0.0.1:15432:5432`) or when the `db` volume holds PostgreSQL 17 data. A `.env` copied from an earlier `example.env` can still set `LAKEKEEPER_IMAGE`, which overrides the new pinned default; delete that line.
- **`nisshi` CLI changes for scripts** ([#1116](https://github.com/nisshi-io/nisshi/pull/1116), [#1121](https://github.com/nisshi-io/nisshi/pull/1121), [#1030](https://github.com/nisshi-io/nisshi/pull/1030)):
  - `nisshi topic create` and `nisshi cat produce` print one line to stdout on success; pass `--silent` to keep the old output.
  - `cat produce` checks all of its input before it sends any. A message without a `"key"` or `"value"` field used to be skipped while the rest were sent, with exit 0. Now the whole run fails with exit 1 and sends nothing.
  - `nisshi user create` exits 1 when the broker refuses a user. Before, it exited 0 whatever the broker answered.
  - The broker banner labels the listener `listener:` (was `listening on:`), and the port-in-use error no longer contains "Address already in use". Errors no longer end with a Rust `Debug` dump.
- **Rollback.** There are no schema changes. On memory, S3 and Google Cloud Storage, 0.7.0 answers ListOffsets `latest` with 0 for a partition that `DeleteRecords` emptied, until the next produce to it ([#1038](https://github.com/nisshi-io/nisshi/pull/1038)). See the retention and topic configuration notes above for what a rollback does to topics changed after the upgrade.
- **Library users.** The library crates change in ways that break existing code:
  - `FetchService` serves a `ValidatedFetchRequest`, and `CreateTopicsService` serves a `ValidatedCreateTopicsRequest`. Put `FetchValidationLayer` and `CreateTopicsValidationLayer` in front of them, as the broker does ([#807](https://github.com/nisshi-io/nisshi/pull/807)).
  - `Storage::list_groups` takes no states filter and returns `Vec<NamedGroupDetail>` ([#1074](https://github.com/nisshi-io/nisshi/pull/1074)).
  - `Storage::produce` must return `Error::MessageTooLarge`, before changing any state, when `max_message_bytes::ensure_batch_fits` rejects the batch ([#1090](https://github.com/nisshi-io/nisshi/pull/1090)).
  - `StorageFactory` now requires `Display` and a `capabilities()` method that returns `StorageCapabilities` ([#1030](https://github.com/nisshi-io/nisshi/pull/1030)). It also has a defaulted `deprecation()` method ([#1126](https://github.com/nisshi-io/nisshi/pull/1126)).
  - `nisshi_storage::Error` gains `AuthenticationUnsupported` and `UserCredentialsUnsupported` ([#1030](https://github.com/nisshi-io/nisshi/pull/1030)) and `MessageTooLarge` ([#1090](https://github.com/nisshi-io/nisshi/pull/1090)). It also gains `NoEngineForScheme`, which `StorageContainer` returns, in place of `FeatureNotEnabled`, for a storage URL whose engine the build lacks ([#1121](https://github.com/nisshi-io/nisshi/pull/1121)).
  - `nisshi_sans_io::Error::FromUtf8` becomes `FromUtf8 { len, error }`. `nisshi_service::Error::UnknownServiceFrame` carries the API key, name and version, the correlation id and the size instead of the frame. `nisshi_broker::Error::StringUtf8` is removed ([#1024](https://github.com/nisshi-io/nisshi/pull/1024)).
  - `nisshi_broker::Error` gains `ListenerInUse` ([#1121](https://github.com/nisshi-io/nisshi/pull/1121)).

### Changed

- On PostgreSQL and SQLite, a topic without a `cleanup.policy` is cleaned by `retention.ms` and `retention.bytes` as Kafka's default policy, `delete`. 0.7.0 skipped such a topic, so a topic that set only a retention limit grew forever ([#1021](https://github.com/nisshi-io/nisshi/pull/1021)).
- `APPEND` to an unset `cleanup.policy` starts from the default, as in Kafka, so `APPEND compact` gives `delete,compact` (it gave `compact`) ([#1021](https://github.com/nisshi-io/nisshi/pull/1021)).
- CreateTopics and IncrementalAlterConfigs check `retention.ms` (a long of at least -1) and `retention.bytes` (a long). An invalid value gets `INVALID_CONFIG` with Kafka's message. A valid value is stored as the number parsed, so ` 600000 ` or `+600000` reads back as `600000`. As in Kafka, IncrementalAlterConfigs checks the value before it checks that the topic exists. CreateTopics answers `TOPIC_ALREADY_EXISTS` for an existing topic whatever its configs ([#1021](https://github.com/nisshi-io/nisshi/pull/1021)).
- On PostgreSQL, Fetch and the retention and compaction sweeps no longer scan the whole `record` table; the compaction change also applies to SQLite with `compaction=single` ([#937](https://github.com/nisshi-io/nisshi/pull/937)):
  - A fetch's cost no longer grows with the backlog. In a 50,000 msg/s benchmark, consumers fell to 0 msg/s within three minutes before this change and now keep up.
  - A fetch reads its headers with one query, not one per record.
  - On 48 million records with nothing to do, a compaction sweep takes 0.2 ms instead of 48 s, and a retention sweep 26 ms instead of 81 s.
  - Retention deletes a record only once both its timestamp and the time it was appended are older than `retention.ms`. A backfilled record with an old timestamp now stays for one retention period after it is written.
- Produce rejects a batch larger than the topic's `max.message.bytes` with `MESSAGE_TOO_LARGE` and Kafka's message, on every engine, and stores nothing ([#1090](https://github.com/nisshi-io/nisshi/pull/1090)):
  - The batch is measured as sent, compressed if the producer compressed it. A topic without the key gets 1048588 bytes.
  - A bad `max.message.bytes` stored by an earlier version gets the default.
  - With produce batching on S3 and Google Cloud Storage (`batch_max_delay`), a merged batch keeps its batches' codec, so merged batches are now stored compressed. A queue that mixes codecs is written one batch at a time, and a merged batch over the limit is written as the batches were sent.
- InitProducerId with a `transactional.id` answers `TRANSACTIONAL_ID_AUTHORIZATION_FAILED` without reaching storage. No storage engine reports aborted transactions, so a `read_committed` consumer read a transactional producer's aborted records as committed ([#1122](https://github.com/nisshi-io/nisshi/pull/1122)).
- DescribeAcls answers `SECURITY_DISABLED` with `No Authorizer is configured on the broker` and no resources. It answered success with an empty list, which told an operator that ACLs are supported and that none exist ([#1079](https://github.com/nisshi-io/nisshi/pull/1079)).
- SaslHandshake lists the enabled mechanisms, `SCRAM-SHA-256` and `SCRAM-SHA-512`, in every response. Before, it listed only the chosen mechanism on success and echoed the requested one on failure. A broker without SASL answers `ILLEGAL_SASL_STATE` with an empty list and keeps the connection open, as a Kafka listener without SASL does; it answered `UNSUPPORTED_SASL_MECHANISM` ([#1028](https://github.com/nisshi-io/nisshi/pull/1028)).
- ListOffsets answers `earliest` and `latest` with timestamp -1 on every engine, as Kafka does. Each engine used to send a batch write time or a record timestamp ([#1038](https://github.com/nisshi-io/nisshi/pull/1038)).
- CreateTopics with manual replica assignments follows Kafka. `num_partitions` and `replication_factor` must both be -1, or the topic gets `INVALID_REQUEST`. The topic gets one partition per assignment, where it got the broker default of 3. The assignments' partition indexes and broker ids are still not honoured ([#807](https://github.com/nisshi-io/nisshi/pull/807)).
- A broker with `--authentication` checks, before it connects to storage, that the engine can store SCRAM users. It exits with an error that names the engine and the engines that can ([#1030](https://github.com/nisshi-io/nisshi/pull/1030)).
- With `RUST_LOG` unset or empty, the broker and every `nisshi` subcommand log at `warn` instead of `error` ([#1115](https://github.com/nisshi-io/nisshi/pull/1115)).
- The `nisshi` commands say what failed and how to fix it ([#1121](https://github.com/nisshi-io/nisshi/pull/1121)):
  - `cat produce` names the input line or array element that isn't valid JSON, isn't a message object, or has no `"key"` or `"value"`, and gives the expected format. It fails on empty input before connecting.
  - When the broker rejects a produce, `cat produce` logs the response's error message and record errors.
  - A broker whose port is in use says so and how to choose another.
  - A storage URL whose engine the build lacks names the cargo feature.
  - A failed connection prints its cause and points at `--broker` (or `ADVERTISED_LISTENER_URL`). It also says these commands connect in plaintext only.
  - Each reported failure starts with `error: `.
- `nisshi_group_coordinator_requests` also counts ListGroups and DescribeGroups, with `method` set to `list_groups` and `describe_groups` ([#1074](https://github.com/nisshi-io/nisshi/pull/1074)).
- Docker Compose: `docker compose up -d nisshi` works on a fresh clone without a `.env` ([#1128](https://github.com/nisshi-io/nisshi/pull/1128), [#1127](https://github.com/nisshi-io/nisshi/pull/1127), [#1137](https://github.com/nisshi-io/nisshi/pull/1137), [#1136](https://github.com/nisshi-io/nisshi/pull/1136)):
  - Each variable has a default: `NISSHI_IMAGE` is `ghcr.io/nisshi-io/nisshi:latest`, storage is PostgreSQL on the `db` service, the cluster id is `nisshi`, the advertised listener is `tcp://localhost:9092`, `RUST_LOG` is `warn`, and the credentials are those of the local object store.
  - Ports are published on `127.0.0.1` only, the broker waits until `db` is healthy, and the `db` healthcheck tests TCP.
  - Images are pinned by digest, so the default `postgres:18` no longer floats to the newest 18.x build.
  - Grafana is 13.2.4 (was 11.5.1), and Prometheus is v3.15.0 (was v3.1.0).

### Deprecated

- The `slatedb://` storage engine ([#1126](https://github.com/nisshi-io/nisshi/pull/1126)). SlateDB allows a single writer, so it isn't recommended for new deployments; use PostgreSQL for production, or SQLite or in-memory storage for development. Existing deployments keep working. The broker logs a warning at startup when the engine is selected, and `nisshi --help` marks it as deprecated. The engine accepts only security fixes and may be removed in a future release.
- The `tansu.*` topic configuration keys, now aliases of the `nisshi.*` keys. The first use of each alias after a start logs one warning that names the key and its replacement, without the value ([#1125](https://github.com/nisshi-io/nisshi/pull/1125)).

### Fixed

- On PostgreSQL and SQLite, `retention.ms=-1`, or any negative value, keeps every record, as in Kafka; before, it deleted every record. On PostgreSQL, a `retention.ms` above 2147483647, such as 30 days, no longer fails the retention statement. That failure stopped retention on every topic. A stored `retention.ms` that isn't a whole number now keeps every record of its topic, and a stored `retention.bytes` that isn't one is ignored. On PostgreSQL such a value failed retention for every topic, and on SQLite a bad `retention.ms` was read as 0, which deleted every record. On SQLite, retention no longer reads every record of a compacted topic, or of one with a negative `retention.ms`, on each sweep while it holds the write lock ([#1021](https://github.com/nisshi-io/nisshi/pull/1021)).
- Produce rejects a batch whose CRC doesn't match its contents with `CORRUPT_MESSAGE`, on every engine, and stores nothing, as Kafka does. A `CreateTime` batch whose `max_timestamp` was already correct skipped the check:
  - The object store engines stored the bad CRC, so every Java consumer of the partition failed on each poll until someone moved its offset past the batch.
  - PostgreSQL, SQLite and Turso served the corrupted records under a new, valid CRC.
  - Gzip and LZ4 batches with a bad CRC got `INVALID_RECORD`.

  The Java producer retries `CORRUPT_MESSAGE`, so a batch damaged in transit succeeds on retry, and a rejected idempotent batch doesn't advance the producer's sequence ([#1029](https://github.com/nisshi-io/nisshi/pull/1029)).
- On memory, S3 and Google Cloud Storage, ListOffsets answers from the partition's watermark, as Kafka does ([#1038](https://github.com/nisshi-io/nisshi/pull/1038)):
  - `earliest` answers the log start. `latest` answers the high watermark, or under `read_committed` the last stable offset.
  - Before, `latest` answered the base offset of the newest batch object plus 1. After any batch of more than one record, lag tools showed negative lag, `--reset-offsets --to-latest` landed inside the last batch, and a consumer that started at the end read that batch again. With several brokers on one bucket, the newest object could also be the wrong batch.
  - Under `read_committed`, `latest` was always 0.
  - A failed read of one partition's watermark answers `KAFKA_STORAGE_ERROR` for that partition only.
  - `DeleteRecords` to the high watermark now also deletes the last batch object.
- On PostgreSQL and SQLite, ListOffsets no longer answers 0 after retention deletes every record of a partition, or only its newest record; the sub-items below also apply to Turso. That 0 made `kafka-consumer-groups --describe` show wrong lag and made `--reset-offsets --to-latest` move a group back to 0 ([#1036](https://github.com/nisshi-io/nisshi/pull/1036)):
  - `latest` answers the high watermark. Under `read_committed` it answers the start of the oldest open transaction, but never less than `earliest`.
  - `earliest` answers the first stored record at or above the log start, or the high watermark when no record is left.
  - For a partition that doesn't exist, both answer `UNKNOWN_TOPIC_OR_PARTITION` and offset -1, as on the other engines, instead of `NONE` and 0.
  - `DeleteRecords` deletes every record below the cut; it used to keep the record at the high watermark minus one.
- CreateTopics with `validate_only` no longer creates the topic, on every engine. A dry run answers `TOPIC_ALREADY_EXISTS` for an existing topic. For a new topic it answers a random topic id with the requested partitions and replication factor, as Kafka does ([#1034](https://github.com/nisshi-io/nisshi/pull/1034)).
- On every engine except SlateDB, DescribeConfigs reports a topic's own configs as `DYNAMIC_TOPIC_CONFIG` instead of `DEFAULT_CONFIG`. `kafka-topics --describe` and `kafka-configs --describe` now list them, and `kafka-configs --delete-config` can remove them ([#1008](https://github.com/nisshi-io/nisshi/pull/1008)).
- ListGroups reports each group's state as one of Kafka's classic group states, and applies the request's state filter, so `kafka-consumer-groups --list --state` works ([#1074](https://github.com/nisshi-io/nisshi/pull/1074)):
  - Every group used to be `Unknown`, and every engine ignored the filter.
  - The states are `Stable`, `Empty`, `PreparingRebalance` and `CompletingRebalance`. A group with only committed offsets is `Empty`.
  - Before reporting a group, ListGroups and DescribeGroups remove members whose session has expired and end a join phase that is past its deadline. A group whose consumers stopped without sending LeaveGroup no longer shows as `Stable` until another request touches it.
  - DescribeGroups and ConsumerGroupDescribe report the same states. A forming group showed as `Assigning` or `Unknown`.
  - A group whose stored state can't be read is listed as `Unknown`, and the rest of the list is still answered.
  - A storage error answers its error code or `COORDINATOR_NOT_AVAILABLE`, for the request in ListGroups and for each group in DescribeGroups. Before, it closed the connection.
- On memory, S3 and Google Cloud Storage, ListGroups lists a consumer group that hasn't committed an offset yet, such as one whose consumers read an idle topic ([#1058](https://github.com/nisshi-io/nisshi/pull/1058), [#1074](https://github.com/nisshi-io/nisshi/pull/1074)).
- On memory, S3 and Google Cloud Storage, DescribeGroups answers `GROUP_ID_NOT_FOUND` for a group that never existed, as Kafka and the SQL engines do. Before, it answered an empty group, so `kafka-consumer-groups --describe` on a mistyped name printed an empty group. A group that only committed offsets is still an empty group. A failed object store read answers `COORDINATOR_NOT_AVAILABLE`, which clients retry, and a stored group that can't be decoded answers `UNKNOWN_SERVER_ERROR`; both were reported as an empty group. DeleteGroups is refused when the group's state can't be read ([#1050](https://github.com/nisshi-io/nisshi/pull/1050)).
- DescribeGroups (v3 and later) and ConsumerGroupDescribe report a group's authorized operations only when the request asks for them, as Kafka does. `Admin.describeConsumerGroups()` gives `null` by default, and `{READ, DESCRIBE, DELETE}` with `includeAuthorizedOperations(true)`. The broker answered -1 on every row, which clients read as every operation, including ones that don't apply to a group ([#1033](https://github.com/nisshi-io/nisshi/pull/1033)).
- ListPartitionReassignments answers that no reassignment is in progress. `kafka-reassign-partitions --list` reported every partition of every topic as being reassigned, so a tool waiting for those reassignments to finish waited forever ([#1031](https://github.com/nisshi-io/nisshi/pull/1031)).
- A client that asks for a SASL mechanism the broker hasn't enabled gets `UNSUPPORTED_SASL_MECHANISM` and the list of enabled mechanisms, and the broker then closes the connection, as Kafka does. An example is `sasl.mechanism=PLAIN` against a broker started with `--authentication`. The Java client now fails at once with `UnsupportedSaslMechanismException`. Before, the broker closed the connection without answering, and the client retried until "Timed out waiting for a node assignment". OAUTHBEARER is no longer advertised or accepted; the handshake accepted it and every authentication then failed ([#1028](https://github.com/nisshi-io/nisshi/pull/1028)).
- `nisshi proxy` handles an `acks=0` producer as a Kafka broker does: the producer reads no response, and nothing stalls ([#1032](https://github.com/nisshi-io/nisshi/pull/1032)):
  - Before, an `acks=0` Produce passed through unbatched held its origin connection for about 35s, waiting for a response that never came. The proxy then closed the client's connection, and the batches pipelined meanwhile were lost.
  - About 256 such producers could stall every client of the proxy.
  - On a batched topic, an `acks=0` client got Produce responses it never asked for, which broke its correlation ids.
  - The proxy now forwards `acks=0` at `acks=1` and discards the response. A partition error closes the client's connection, as Kafka does.

  This removes the known limitation in the 0.7.0 upgrade notes.
- On memory, S3, Google Cloud Storage and null storage, AlterUserScramCredentials answers each user with `UNSUPPORTED_VERSION` and a message saying nothing was stored. Before, on memory, S3 and Google Cloud Storage it reported success and stored nothing, and on null storage it answered `UNSUPPORTED_SASL_MECHANISM` with no message. `kafka-configs --alter --entity-type users` prints the message and exits 1. On Turso, the same answer replaces a panic of the client's connection. `nisshi user create` prints the broker's message and code for each user that failed ([#1030](https://github.com/nisshi-io/nisshi/pull/1030)).
- Responses no longer leave out a required array that the broker left unset, or the presence marker of a non-null nullable struct. Either one made the client fail to read the rest of the response ([#807](https://github.com/nisshi-io/nisshi/pull/807)):
  - DescribeUserScramCredentials (`kafka-configs --describe --entity-type users`) answers an empty list, where clients couldn't read its response. It still doesn't list stored users.
  - CreateAcls answers `SECURITY_DISABLED` with `No Authorizer is configured.` for each creation. Its empty response desynced clients.
- A DescribeConfigs request that names the config keys to return now decodes; the broker failed to decode it and closed the connection. A tagged field longer than 128 bytes now decodes instead of being rejected ([#807](https://github.com/nisshi-io/nisshi/pull/807)).
- These malformed requests get an error code instead of closing the connection ([#807](https://github.com/nisshi-io/nisshi/pull/807)):
  - Fetch with an invalid `isolation_level`, `max_wait_ms`, `min_bytes` or `max_bytes` gets `INVALID_REQUEST`.
  - ListOffsets with an invalid `isolation_level` gets `INVALID_REQUEST`, where Kafka answers `UNKNOWN_SERVER_ERROR`.
  - ListOffsets with an unsupported timestamp gets `INVALID_TIMESTAMP`.
  - AlterUserScramCredentials with an unknown mechanism gets `UNSUPPORTED_SASL_MECHANISM`.

  A Fetch or Metadata topic that has neither a name nor an id no longer panics the connection.
- Two brokers that start at the same time on an empty PostgreSQL database no longer fail with `duplicate key value violates unique constraint "nisshi_schema_version_pkey"`. The schema setup runs at READ COMMITTED, whatever default isolation level the storage URL's `options` set ([#1010](https://github.com/nisshi-io/nisshi/pull/1010)).
- On PostgreSQL, a fetch of a virtual keyed topic (`topic/key`) returns the records' headers; it returned none ([#937](https://github.com/nisshi-io/nisshi/pull/937)).
- On Windows, the broker starts with a bare relative SQLite path such as `sqlite://nisshi.db` or `sqlite://nisshi.db/`. It failed to open `nisshi.db\` ([#1037](https://github.com/nisshi-io/nisshi/pull/1037)).
- `nisshi cat produce` can produce to a topic that doesn't exist yet. It asks the broker to create the topic, which the broker does when it allows auto-creation. Before, the produce failed with `UnknownTopicOrPartition` ([#1037](https://github.com/nisshi-io/nisshi/pull/1037)).
- `cargo install nisshi` builds a broker that starts. The crate's default features are now `dynostore`, `libsql` and `postgres`. Before, they included no storage engine, so the broker failed on its own default `--storage-engine` ([#1105](https://github.com/nisshi-io/nisshi/pull/1105)).
- docs.rs builds the documentation of `nisshi-storage`, `nisshi-storage-sql` and `nisshi-broker` again, without the Turso items; it had failed since 0.7.0-pre.3. Building `nisshi-storage-sql` or `nisshi-broker` without the `turso` feature no longer compiles Turso ([#1042](https://github.com/nisshi-io/nisshi/pull/1042)).

### Security

- A request that fails to decode, or that the broker doesn't route, no longer writes its bytes to the log. On the default configuration, one unauthenticated client could make the broker write about 10 bytes of ERROR log per request byte, for requests up to the 100 MiB frame limit. Each failure now logs one short line ([#1024](https://github.com/nisshi-io/nisshi/pull/1024)).
- `nisshi proxy` and the CLI tools bound each length-prefixed field of a response to the frame it arrived in. A malicious or faulty upstream broker could make them reserve up to 1 GiB of address space for each response they decoded ([#1022](https://github.com/nisshi-io/nisshi/pull/1022)).
- Dependency updates:
  - zstd 0.14.3 and zstd-safe 8.2.0 (from 0.14.0 and 8.0.0), the codec for record batches, for [RUSTSEC-2026-0391](https://rustsec.org/advisories/RUSTSEC-2026-0391) (zstd), and [RUSTSEC-2026-0398](https://rustsec.org/advisories/RUSTSEC-2026-0398) and [RUSTSEC-2026-0403](https://rustsec.org/advisories/RUSTSEC-2026-0403) (zstd-safe) ([#1098](https://github.com/nisshi-io/nisshi/pull/1098)). Several dependencies, including apache-avro, iceberg, datafusion, parquet, arrow and foyer, still use zstd 0.13, which has no fixed release.
  - rustls-webpki 0.103.16 and webpki-root-certs 1.0.10 for [RUSTSEC-2026-0382](https://rustsec.org/advisories/RUSTSEC-2026-0382) and [RUSTSEC-2026-0383](https://rustsec.org/advisories/RUSTSEC-2026-0383). Certificate verification could accept a chain through distrusted intermediate certificates whose private keys are publicly known ([#1048](https://github.com/nisshi-io/nisshi/pull/1048)).
  - tokio 1.54.1 for [RUSTSEC-2026-0386](https://rustsec.org/advisories/RUSTSEC-2026-0386). Nisshi doesn't call the affected `AsyncFd` constructors ([#1088](https://github.com/nisshi-io/nisshi/pull/1088)).
  - ctutils 0.4.5 for [RUSTSEC-2026-0385](https://rustsec.org/advisories/RUSTSEC-2026-0385) ([#1088](https://github.com/nisshi-io/nisshi/pull/1088)).

## [0.7.0] - 2026-10-16

### Upgrade notes

- **The project is now Nisshi (formerly Tansu).** The binary is `nisshi`, the image is `ghcr.io/nisshi-io/nisshi`, and the crates are `nisshi-*`. Prefixed metrics are named `nisshi_*` instead of `tansu_*`, `RUST_LOG` targets are `nisshi_broker`, `nisshi_storage` and so on, and the default OpenTelemetry `service.name` is `nisshi-broker`, `nisshi-proxy` or `nisshi-generator`. Update dashboards, alerts and log filters. Topic configuration keys keep their `tansu.` prefix (`tansu.batch`, `tansu.lake.*`, `tansu.virtual`).
- **The default cluster id is now `nisshi_cluster` (was `tansu_cluster`).** Every storage engine keys its data by cluster id, so a broker upgraded without `--cluster-id` or `CLUSTER_ID` starts on an empty cluster. Set `CLUSTER_ID=tansu_cluster` to keep using existing data. The default storage engine is now `memory://nisshi/`.
- **SlateDB: the database path is now `nisshi-<cluster id>.slatedb` (was `tansu-<cluster id>.slatedb`).** Setting `CLUSTER_ID=tansu_cluster` alone doesn't find existing SlateDB data, which stays under `tansu-<cluster id>.slatedb/` in the bucket. A `slatedb://` or `s3://` URL without a bucket now defaults to bucket `nisshi` (was `tansu`).
- **Lake defaults: `ICEBERG_NAMESPACE` and `DELTA_DATABASE` default to `nisshi` (were `tansu`).** A broker upgraded without them writes Iceberg tables to a new namespace and Delta tables to new `nisshi.<topic>` paths. Set `ICEBERG_NAMESPACE=tansu` and `DELTA_DATABASE=tansu` to keep writing the existing tables.
- **PostgreSQL, SQLite and Turso schema changes, with no automatic migration** ([#715](https://github.com/nisshi-io/nisshi/pull/715), [#655](https://github.com/nisshi-io/nisshi/pull/655), [#712](https://github.com/nisshi-io/nisshi/pull/712)):
  - The `header` table gains an `ordinal` column and is keyed on `(topition, offset_id, ordinal)`, so headers keep their produce order and a record can repeat a header key. Produce and Fetch fail against the old table. Recreate the database, or on PostgreSQL migrate it by hand with the statements from #715:
    ```sql
    alter table header add column ordinal int;
    update header h set ordinal = n.rn - 1
    from (select topition, offset_id, k,
                 row_number() over (partition by topition, offset_id order by k) as rn
          from header) n
    where h.topition = n.topition and h.offset_id = n.offset_id and h.k = n.k;
    alter table header alter column ordinal set not null;
    alter table header drop constraint header_pkey;
    alter table header add primary key (topition, offset_id, ordinal);
    ```
    On SQLite and Turso, rebuild the table to the definition in `nisshi-storage-sql/src/ddl/040-header.sql`, or recreate the database.
  - PostgreSQL has a new `virtual_topic` table, which lookups by topic id read. The broker creates it at startup, as on SQLite and Turso.
  - PostgreSQL `txn_detail.started_at` is now `timestamptz`, so the transaction timeout sweep measures elapsed time correctly when the server is not on UTC. An existing database keeps `timestamp`. If its server is not on UTC, drop the `v_txn_detail` view and run `alter table txn_detail alter column started_at type timestamptz` before starting the upgraded broker, which recreates the view.
- **The broker creates the PostgreSQL and SQLite schema at startup** and records its version in a new `nisshi_schema_version` table ([#987](https://github.com/nisshi-io/nisshi/pull/987)). A new deployment needs no setup step, and the `etc/initdb.d` scripts, which Docker Compose's PostgreSQL ran on its first start, are gone. The broker creates only what is missing and never changes existing tables, so its database role must be able to create tables and replace views; a role that can't stops the broker with an error that says so. A database from an earlier release is recorded as schema version 1 without its tables being checked, so make the `header` and `txn_detail` changes above before its first start. The broker refuses to start on a database whose recorded schema is older than its own, or newer and incompatible. If the setup fails, the broker stops; SQLite used to log the failed statement and start with tables missing. PostgreSQL 13 or later is required. Turso keeps running its DDL at startup and records no version.
- **`--cert` and `--key` now serve TLS.** Before, the two flags together failed at argument parsing, and either flag alone was accepted and ignored, so the broker only ever served plaintext. The two flags together now serve TLS only, and plaintext clients are refused at the handshake. Either flag alone is now an error, and a certificate or key that does not load stops the broker with an error that names the file ([#735](https://github.com/nisshi-io/nisshi/pull/735)).
- **S3 and in-memory (DynoStore): some consumer group keys move, with no migration** ([#842](https://github.com/nisshi-io/nisshi/pull/842)). The engine stores each consumer group id as exactly one segment of its object key. Keys for other ids are unchanged. These keys move, and data under the old keys is not migrated:
  - an id containing `/`: its committed offsets and group state;
  - the empty id `""`, which consumers using `assign()` commit under: its committed offsets and group state;
  - `.` and `..`: the group state only.

  An affected group's consumers find no committed offset and start from `auto.offset.reset`. With the Java client default, `latest`, they skip records they had not yet consumed. Old data stays visible in ListGroups: old `""` data lists as a group named `offsets`, and old `a/b` data as a group named `a`. Deleting that group removes it. Upgrade every broker sharing a bucket before using these ids: an old and a new broker read and write different keys for them, so members connected to different brokers form two separate groups. A rollback returns these groups to the offsets they had before the upgrade.
- **S3 and in-memory (DynoStore): keys for a topic whose name contains `/` move to one encoded segment, with no migration.** Objects under the old keys stay in place. CreateTopics rejects such names in this release, so only topics created by an earlier version are affected ([#977](https://github.com/nisshi-io/nisshi/pull/977)).
- **SlateDB: consumers below the log start offset now reset.** A consumer whose position is below a partition's log start offset now applies `auto.offset.reset`, as with Apache Kafka: Fetch answers `OFFSET_OUT_OF_RANGE` straight away, where it used to return the earliest surviving record. This shows on SlateDB after retention, DeleteRecords, or compaction by an earlier version: `v0.7.0-pre.1` and `v0.7.0-pre.2` moved the log start to the first surviving batch on compaction, and their Fetch had no bounds check, so a consumer behind that log start read the first surviving batch. After the upgrade that log start stays where it is, so on a compacted SlateDB topic a group that is offline or lagging resets for the first time. With the default `latest`, the consumer skips the retained backlog, which on a topic that rewrites a few keys often (such as a config topic) can be nearly all of it; with `none`, the application gets an exception. Before you upgrade, compare each group's committed offsets with ListOffsets `earliest` on SlateDB topics, compacted ones in particular, and reset lagging groups to `earliest`. Run consumers of compacted SlateDB topics with `auto.offset.reset=earliest` across the upgrade, because compaction by the old version keeps raising the log start between that check and the upgrade itself. The log start is the batch the old version would have served, so a reset to it loses nothing. These answers are counted in `nisshi_fetch_offset_out_of_bounds` with `bound` set to `below_log_start`, which after the upgrade also shows consumers that the group comparison misses, such as those that use `assign` with offsets stored outside Kafka ([#826](https://github.com/nisshi-io/nisshi/pull/826)).
- **Listener defaults.** The broker's default `--listener-url` is now `tcp://[::]:9092`, which accepts both IPv6 and IPv4 clients. On a host without IPv6 support, Windows included, the broker falls back to `0.0.0.0` on the same port and logs a warning ([#894](https://github.com/nisshi-io/nisshi/pull/894)); set `LISTENER_URL=tcp://0.0.0.0:9092` to listen on IPv4 only. The default advertised listener, the default broker URL of the `nisshi` client subcommands, and `nisshi proxy`'s default `--origin-url` and advertised listener are now `127.0.0.1:9092` instead of `localhost:9092`, so a client whose resolver returns `::1` for `localhost` first no longer gets connection refused ([#843](https://github.com/nisshi-io/nisshi/pull/843)).
- **Configuration the broker used to ignore now stops it at startup** ([#850](https://github.com/nisshi-io/nisshi/pull/850), [#844](https://github.com/nisshi-io/nisshi/pull/844)):
  - a storage URL query option that the storage engine does not read, such as a misspelt option or `vacuum_into` on an `s3://` or `slatedb://` URL. The error names the option and the engine (PostgreSQL already rejected unknown options);
  - `maintenance_interval` or `transaction_maintenance_interval` with an invalid value: unparsable, zero, longer than 365 days, or a bare number without a unit. Previously an unparsable value fell back to the default interval, and zero panicked the maintenance task. Give a bare number its unit, for example `600s` or `10m` instead of `600`. Compound values such as `1h30m` and `5min` still work;
  - a `parquet`, `iceberg` or `delta` broker without `--schema-registry` stops with an error that names the missing option, instead of panicking. `--schema-registry` is accepted before or after the subcommand;
  - a broker on S3 or Google Cloud Storage exits when it cannot list its cluster's prefix in the bucket, or when its AWS credential provider does not return a credential. The error names the storage URL and the cause. Previously the broker started and failed on its first request.
- **Upgrade `nisshi proxy` before the brokers behind it.** The proxy forwards a batched Produce (`tansu.batch=true`) with the strictest `acks` among the batched requests, and at least `acks=1`, so the origin answers it. An older proxy forwards batches with `acks=0` and waits for a response that an upgraded broker no longer sends. Known limitation: the proxy still waits for a response to an `acks=0` Produce that it passes through unbatched. Against an upgraded broker, that request stalls until the broker's connection idle timeout closes the upstream connection ([#845](https://github.com/nisshi-io/nisshi/pull/845)).
- **`nisshi proxy` no longer forwards SASL.** It answers SaslHandshake and SaslAuthenticate itself with `ILLEGAL_SASL_STATE`. Clients must connect to the proxy with `security.protocol=PLAINTEXT`, and the origin listener must not require authentication ([#993](https://github.com/nisshi-io/nisshi/pull/993)).
- **Advertised API versions are narrower:** Produce 3-11 (was 0-11), ListOffsets 0-6 (was 0-9), AddPartitionsToTxn 0-3 (was 0-5), and GetTelemetrySubscriptions is no longer advertised. A request at a version outside the advertised range closes the connection, except ApiVersions, which is answered with `UNSUPPORTED_VERSION`. The Java admin client's `OffsetSpec.maxTimestamp()`, `earliestLocal()` and `latestTiered()` now fail in the client ([#849](https://github.com/nisshi-io/nisshi/pull/849)).
- **Produce validation is stricter.** Batches the broker used to store now get an error: a record timestamped more than an hour ahead of the broker's clock (`INVALID_TIMESTAMP`), and with `INVALID_RECORD` a batch whose `last_offset_delta` disagrees with `record_count`, a client batch with the control bit set, more than one batch per partition, an unknown compression codec, a record that does not decode, and a compressed record whose declared length is wrong or a compressed batch with bytes after its last record; and with `MESSAGE_TOO_LARGE` a batch that decodes to more than 100 MiB. Well-formed producers see no change. See Changed and Security for each.
- **PostgreSQL and SQLite partitions damaged by an earlier version.** A batch whose `last_offset_delta` did not match its record count, such as the one the README quickstart (`nisshi cat produce taxi etc/data/trips.json`) sent, wedged its partition. This release stops new damage but does not repair it. A partition is damaged when `max(record.offset_id)` for its topition is at or above its `watermark.high`; set that partition's `watermark.high` to `max(record.offset_id) + 1`. DynoStore and SlateDB don't wedge, but later batches can overlap earlier offsets; recreate the topic ([#783](https://github.com/nisshi-io/nisshi/pull/783)).
- **PostgreSQL timeouts.** A pool checkout waits at most 10s, and each statement, except in the retention and compaction sweeps, has a server-side `statement_timeout` of 30s unless the storage URL sets one; both answer `REQUEST_TIMED_OUT`, which clients retry. The timeout is sent as a startup `options` parameter, which PgBouncer rejects by default, so a broker behind PgBouncer fails to start ([#730](https://github.com/nisshi-io/nisshi/pull/730)).
- **Consumer group rebalances follow Kafka's timing.** Every empty group waits `--group-initial-rebalance-delay` (3s) on its first join, as on Kafka, and `JoinGroup` and `SyncGroup` are held until the phase ends, up to the rebalance timeout. The first generation is 1, and a static member that restarts gets a new member id. The `method` label values `join_follower_pause` (`join_group_pause` in the 0.7.0 pre-releases), `join_group_instance_pause` and `sync_group_instance_pause` of the coordinator request counter are replaced by `join_held` and `sync_held`; update dashboards that use them ([#990](https://github.com/nisshi-io/nisshi/pull/990)).
- **Idle and stalled connections are closed.** A connection with no request for 10 minutes (Kafka's `connections.max.idle.ms` default) is closed, and so is one whose transfer stalls for 30s ([#729](https://github.com/nisshi-io/nisshi/pull/729)).
- **OpenTelemetry.** The metrics `service.name` now comes from `OTEL_SERVICE_NAME`, then `service.name` in `OTEL_RESOURCE_ATTRIBUTES`. A broker that inherits either variable, for example injected for another agent, exports its series under that name; unset it or set `OTEL_SERVICE_NAME=nisshi-broker`. `v1/metrics` is now appended to the endpoint path, so `http://gateway/otlp` exports to `http://gateway/otlp/v1/metrics` instead of `http://gateway/v1/metrics` ([#740](https://github.com/nisshi-io/nisshi/pull/740)). An invalid `OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE` now stops a broker with an OTLP endpoint at startup ([#804](https://github.com/nisshi-io/nisshi/pull/804)).
- **S3 and in-memory: ListOffsets by timestamp** can land on a different offset after the upgrade, because it now answers from record timestamps. The first lookup on each existing partition reads every stored batch to build a time index. Upgrade every broker sharing a bucket before relying on these lookups, because a produce from an older broker discards the partition's time index ([#840](https://github.com/nisshi-io/nisshi/pull/840)).
- **Rollback.** SlateDB writes manifest format v2, which an older broker cannot open ([#802](https://github.com/nisshi-io/nisshi/pull/802)). On PostgreSQL, SQLite and Turso, rows now keep the producer's codec, and an older broker fails to fetch a partition holding a Snappy row ([#734](https://github.com/nisshi-io/nisshi/pull/734)).
- **Release artifacts.** The Linux tarballs are static musl binaries built with every storage engine, and there is no Intel macOS binary any more (see Changed and Removed).
- **Library users.** The storage engines moved to their own crates (`nisshi-storage-dynostore`, `-sql`, `-slatedb`, `-null`), and `StorageContainer` needs each engine's factory registered. The service crates use rama 0.4, `nisshi_schema::Error` and `nisshi_service::Error` changed, `TcpContext::default()` now bounds frames at 100 MiB, the `Storage` trait has a new required method, `group_with_version` ([#989](https://github.com/nisshi-io/nisshi/pull/989)), and `nisshi_storage::Error` gains `StartupFailed`, `IncompatibleSchema` and `OutdatedSchema` ([#987](https://github.com/nisshi-io/nisshi/pull/987)). See Changed. Building from source uses Rust 1.98 (was 1.94).

- Release binaries embed their crate list (`cargo auditable`), so image scanners such as Trivy and Grype can read it ([#891](https://github.com/nisshi-io/nisshi/pull/891)).
- A multi-arch `ghcr.io/nisshi-io/nisshi:edge` image of `main`, published by the scheduled CI run once `main`'s tip has passed CI. It is also tagged `main` for now ([#966](https://github.com/nisshi-io/nisshi/pull/966)).

### Changed

- Each route advertises only the API versions it implements, and a request outside that range, or outside the protocol range, closes the connection and logs a warning. ApiVersions above v4 is answered at v0 with `UNSUPPORTED_VERSION`, and ListOffsets v0 now gets `old_style_offsets` ([#849](https://github.com/nisshi-io/nisshi/pull/849)).
- Fetch answers straight away, instead of after `max_wait`, when any partition is `OFFSET_OUT_OF_RANGE` or every partition has an error. A consumer assigned only to a deleted topic now fetches at its error backoff rather than once per `max_wait` ([#826](https://github.com/nisshi-io/nisshi/pull/826)).
- Each Fetch partition's reads are bounded by a share of a `max_wait + 5s` deadline, so one slow partition no longer starves the partitions after it. A partition that stalls answers with what it has read ([#852](https://github.com/nisshi-io/nisshi/pull/852)). On PostgreSQL an abandoned Fetch read cancels its statement, and at most 8 Fetch reads run at once, apart from the 8 for ListOffsets ([#997](https://github.com/nisshi-io/nisshi/pull/997)).
- ListOffsets reads up to 4 partitions at once under a 5s deadline, and a partition not read in time answers `REQUEST_TIMED_OUT`. On PostgreSQL a dropped read cancels its statement ([#827](https://github.com/nisshi-io/nisshi/pull/827)).
- Produced batches are decoded on Tokio's blocking pool, so a large compressed batch no longer holds up other connections on the same worker ([#851](https://github.com/nisshi-io/nisshi/pull/851)), and a compressed batch decodes about 30 to 110 times faster ([#969](https://github.com/nisshi-io/nisshi/pull/969)).
- A `CreateTime` batch's `max_timestamp` is rewritten from its records when they disagree, and a record more than an hour ahead of the broker's clock is rejected with `INVALID_TIMESTAMP`, as Kafka's `log.message.timestamp.after.max.ms` default does ([#847](https://github.com/nisshi-io/nisshi/pull/847)).
- Produce answers `INVALID_RECORD`, instead of `UNKNOWN_SERVER_ERROR` or storing the batch, for: a batch that does not decode, an unknown compression codec, more than one batch for a partition ([#853](https://github.com/nisshi-io/nisshi/pull/853)); a batch whose `last_offset_delta + 1` is not its `record_count` ([#783](https://github.com/nisshi-io/nisshi/pull/783)); and a compressed record whose declared length is wrong, or a compressed batch with bytes after its last record, as Kafka does ([#969](https://github.com/nisshi-io/nisshi/pull/969)). A `LogAppendTime` batch on the memory, S3, GCS and SlateDB engines is still stored without being decoded, unless a schema registry or data lake is configured.
- CreateTopics checks each topic before storage, also under `validate_only`, and answers as Kafka does: `INVALID_TOPIC_EXCEPTION` for a name outside 1 to 249 characters of `[A-Za-z0-9._-]`, or `.` or `..`; `INVALID_PARTITIONS` for 0 or below -1 partitions ([#786](https://github.com/nisshi-io/nisshi/pull/786)); and `POLICY_VIOLATION` for every topic of a request asking for more than 10,000 partitions in total ([#830](https://github.com/nisshi-io/nisshi/pull/830)).
- CreateTopics rejects a replication factor above 64 with `INVALID_REPLICATION_FACTOR`, and its error message names the cause. Metadata and DescribeTopicPartitions list at most 64 replicas per partition; a topic stored with a factor from 1 to 64 describes as before ([#996](https://github.com/nisshi-io/nisshi/pull/996)).
- The group coordinator follows Kafka 3.9.1's classic coordinator, so rebalances take as long as on Kafka instead of several times longer (a first record after about 7s instead of 24s with default clients). The join phase ends as soon as every member has rejoined, or at the rebalance timeout; a dynamic member that didn't rejoin, or a member that didn't send `SyncGroup` in time, is removed. `Heartbeat`, `SyncGroup` and `OffsetCommit` answer with Kafka's error code in each state, and `MEMBER_ID_REQUIRED` goes only to `JoinGroup` v4 and later. The state of a rebalance is stored with the group, so any broker sharing the storage can complete it, and held requests no longer rewrite the group in a loop. New broker flags: `--group-initial-rebalance-delay` (`GROUP_INITIAL_REBALANCE_DELAY`, default `3s`) and `--group-poll-interval` (`GROUP_POLL_INTERVAL`, default `500ms`) ([#990](https://github.com/nisshi-io/nisshi/pull/990)).
- JoinGroup answers `INVALID_SESSION_TIMEOUT` for a `session_timeout_ms` of 0 or less, or above 30 minutes ([#788](https://github.com/nisshi-io/nisshi/pull/788)).
- The broker and proxy bound request frames at 100 MiB by default (`TcpContext::default()`), and a negative length prefix closes the connection with `InvalidFrameLength` ([#723](https://github.com/nisshi-io/nisshi/pull/723)).
- When the broker closes the connection of a client that sends a request other than ApiVersions, SaslHandshake or SaslAuthenticate before it authenticates, it logs an ERROR line that names the client's address ([#850](https://github.com/nisshi-io/nisshi/pull/850)).
- `nisshi proxy` and the CLI tools bound every wait on the broker they connect to ([#885](https://github.com/nisshi-io/nisshi/pull/885), [#882](https://github.com/nisshi-io/nisshi/issues/882)):
  - A request fails with `Timeout` when the broker does not answer within 30s. A request that asks the broker to wait (Fetch, Produce, JoinGroup, and the topic and partition admin requests) gets that wait plus 5s instead, when that is longer, with the wait capped at 5 minutes. `nisshi proxy` then closes the client's connection, and the client retries.
  - A request fails with `Pool(Timeout(Wait))` after 30s without a free connection, and with `Pool(Timeout(Create))` when a new connection takes more than 30s to open.
  - `nisshi proxy` opens up to 256 connections to its origin, instead of twice the number of CPUs.
  - `nisshi_client::Builder` sets these with `request_timeout`, `max_request_wait`, `wait_timeout`, `connect_timeout`, `max_idle` and `max_size`.
- InitProducerId follows Apache Kafka 3.9.1 on every storage engine when a producer sends its current producer ID and epoch to bump its epoch after an error ([KIP-360](https://cwiki.apache.org/confluence/display/KAFKA/KIP-360%3A+Improve+reliability+of+idempotent%2Ftransactional+producer), [#887](https://github.com/nisshi-io/nisshi/pull/887)):
  - Without a transactional ID, the producer gets a new producer ID, whatever it sends.
  - With a transactional ID that has no producer yet, the broker creates one.
  - With a transactional ID that has a producer, the broker bumps the epoch only when the request has that producer's ID and current epoch. Otherwise it answers `PRODUCER_FENCED`. On PostgreSQL, this replaces `UNKNOWN_PRODUCER_ID` for an unknown producer ID.
  - A request that sets only one of producer ID and epoch to -1 gets `INVALID_REQUEST`.
  - A failed InitProducerId answers producer ID and epoch -1, and the broker logs the request at info.
  - Two differences from Apache Kafka remain. Kafka also accepts the previous epoch, from a producer that retries a bump whose response it lost; the broker answers `PRODUCER_FENCED`, and the producer must initialise again. Kafka answers `INVALID_PRODUCER_EPOCH` instead of `PRODUCER_FENCED` to InitProducerId v3 and older; the broker answers `PRODUCER_FENCED` at every version.
- IncrementalAlterConfigs follows Apache Kafka 3.9.1 ([#888](https://github.com/nisshi-io/nisshi/pull/888)):
  - Each resource is checked the way Kafka does, and each failing resource gets its own error without closing the connection: `INVALID_REQUEST` for a resource that appears twice, duplicate config keys, a null value on any operation except `DELETE`, or an unknown operation; `INVALID_CONFIG` for `APPEND` or `SUBTRACT` on a key whose type isn't a list (the topic list keys are `cleanup.policy`, `leader.replication.throttled.replicas` and `follower.replication.throttled.replicas`); `UNKNOWN_TOPIC_OR_PARTITION` for a topic that doesn't exist, on every storage engine. The memory, S3, GCS and SlateDB engines used to report success.
  - `validate_only` no longer changes anything. It used to apply the changes.
  - A topic applies all the changes of one resource, or none of them. A storage failure fails only that resource, with `UNKNOWN_SERVER_ERROR`.
  - `APPEND` and `SUBTRACT` follow Kafka: each item of a comma-separated value is added if missing, or its first occurrence is removed. An unset value is an empty list. Kafka starts from the key's default instead, so `APPEND compact` to an unset `cleanup.policy` gives `compact` here and `delete,compact` in Kafka. Nisshi deletes old records only when `cleanup.policy` contains `delete`.
- PostgreSQL pool checkouts and statements are bounded (10s and 30s), and both timeouts answer `REQUEST_TIMED_OUT`. Maintenance sweeps are exempt from the statement timeout ([#730](https://github.com/nisshi-io/nisshi/pull/730)).
- A connection idle for 10 minutes, or a transfer stalled for 30s, is closed, and the broker reads a frame as its bytes arrive instead of allocating its declared size up front ([#729](https://github.com/nisshi-io/nisshi/pull/729)).
- The Linux release tarballs are static musl binaries built with every storage engine (they were glibc builds without `slatedb` and `turso`). They run on older distributions such as Rocky 8, Amazon Linux 2 and Ubuntu 20.04. The image and the tarballs use the same binary, so the image's arm64 binary is now built natively instead of cross-compiled ([#755](https://github.com/nisshi-io/nisshi/pull/755)).
- OTLP metric exports retry up to 3 times on 429, 502, 503 or 504 ([#924](https://github.com/nisshi-io/nisshi/pull/924)).
- On the memory, S3 and GCS engines, an out-of-order or duplicate producer sequence number is no longer logged as an error.
- `nisshi_schema::Error`: `AvroToJson` and `InvalidValue` hold an Avro `SchemaKind`, and `JsonToAvro` and `UnsupportedSchemaRuntimeValue` hold the kind of JSON value, in place of the value. `JsonToAvroFieldNotFound` no longer has a `value` field. The new `AvroRecord` variant reports an Avro record that fails to read or write against its schema, without the `apache_avro` error, whose message holds the record's values ([#889](https://github.com/nisshi-io/nisshi/pull/889)).
- Library crates: the storage engines moved out of `nisshi-storage` into `nisshi-storage-dynostore`, `nisshi-storage-sql`, `nisshi-storage-slatedb` and `nisshi-storage-null`, and `StorageContainer` dispatches through each registered engine's `StorageFactory`. The service layers use rama 0.4.
- The pinned Rust toolchain is 1.98 (was 1.94).
- The Docker Compose stack's broker service is `nisshi`, and its image variable is `NISSHI_IMAGE` (was `TANSU_IMAGE`). PostgreSQL defaults to 18, which doesn't use a `db` volume created by 17; set `POSTGRES_IMAGE=postgres:17` or recreate the volume.

### Removed

- The broker no longer advertises GetTelemetrySubscriptions ([KIP-714](https://cwiki.apache.org/confluence/display/KAFKA/KIP-714%3A+Client+metrics+and+observability)), which had nothing behind it ([#849](https://github.com/nisshi-io/nisshi/pull/849)).
- The `nisshi_storage_container_requests` and `nisshi_storage_container_errors` metrics (`tansu_storage_container_*` in 0.6.0) are no longer recorded.

### Fixed

- On PostgreSQL, SQLite and Turso, DeleteTopics deleted every topic and record in the cluster ([#714](https://github.com/nisshi-io/nisshi/pull/714)).
- On S3 and in-memory storage, a consumer group whose id contains `/` or is empty no longer shares offsets or group state with another group. Group `a/` no longer reads or overwrites the committed offsets of group `a`, deleting group `a` no longer deletes group `a/b`, and DeleteGroups for an empty id no longer deletes every group. Deleting a topic now also removes the committed offsets that such groups hold for it ([#842](https://github.com/nisshi-io/nisshi/pull/842), [#784](https://github.com/nisshi-io/nisshi/pull/784)).
- On S3 and in-memory storage, ListGroups returns each group's real id. For an id with a reserved character it returned the encoded form (`a%23b` for `a#b`, `%2E` for `.`), which DescribeGroups and DeleteGroups could not find ([#842](https://github.com/nisshi-io/nisshi/pull/842)).
- DeleteTopics on the object-store backends (`s3://`, `gs://`, `memory://`) no longer deletes other topics' data or committed offsets when the deleted topic's name is empty or contains `/`. Such a topic is removed from metadata and the request answers `NONE`. The data of a topic named `""` stays in the bucket; for a name containing `/`, data written by this release is deleted and objects under the old keys stay. Committed offsets stay when the name has an empty segment (`a/`, `/a`, `a//b`, or empty). The broker logs each kept location at `warn` with the topic id. Do not delete those objects by key prefix: for several of these names they share keys with a live topic of the plain name, and must stay while it exists. Creating a topic whose name collapses onto such kept objects (`a` after `a/` was deleted) finds them in place and its first produce fails; delete `a` and create it again ([#833](https://github.com/nisshi-io/nisshi/pull/833), [#977](https://github.com/nisshi-io/nisshi/pull/977)).
- `DeleteGroups` refuses a group that still has members with `NON_EMPTY_GROUP` (68), instead of deleting its state and committed offsets out from under a live consumer. A member whose session has expired does not count. The broker decides from stored group state, so a member connected through another broker counts too, and a group whose state the storage engine reports it cannot read is not deleted. The S3 and in-memory storage engine still reports a group whose state object it cannot fetch as an empty group; this is tracked separately. Only the broker that served the request forgets its cached state for the deleted group; another broker that cached the group can still write it back. A group named more than once in one request is processed once ([#837](https://github.com/nisshi-io/nisshi/pull/837)).
- `DescribeGroups` on the PostgreSQL and libSQL (including Turso) storage engines report a group that only ever committed offsets, and never ran `JoinGroup`, as an empty group instead of failing ([#837](https://github.com/nisshi-io/nisshi/pull/837)).
- The broker no longer writes a Produce response for an `acks=0` request. A storage or validation failure on an `acks=0` Produce now closes the connection (matching Apache Kafka) instead of silently dropping the batch. `nisshi-generator` and `nisshi-perf` now produce with `acks=1` ([#845](https://github.com/nisshi-io/nisshi/pull/845)).
- Fetch checks the fetch offset before it reaches the storage engine, so a storage engine never receives an offset such as `i64::MAX`. Above the high watermark, Fetch answers `NONE` with no records on every engine. Apache Kafka answers `NONE` only up to the log end offset and `OFFSET_OUT_OF_RANGE` above it; Nisshi answers `NONE` because a broker on dynostore can read a high watermark that lags a write through another broker. A consumer whose position is past the end of the log therefore waits there instead of applying `auto.offset.reset`. Such a consumer shows in `nisshi_fetch_offset_out_of_bounds` with `bound` set to `above_high_watermark`, counted once per poll round of a Fetch, so the counter shows whether parked fetches exist rather than how many; a short burst on dynostore with several brokers is expected ([#826](https://github.com/nisshi-io/nisshi/pull/826)).
- Fetch no longer sends a `current_leader` hint with `UNKNOWN_TOPIC_OR_PARTITION`, as in Apache Kafka, which sends one only with a leadership error. librdkafka acts on the hint, and with Fetch now answering an unknown topic straight away, its consumers hung or crashed on close after their topic was deleted ([#826](https://github.com/nisshi-io/nisshi/pull/826)).
- Fetch for a topic name that doesn't exist now answers `UNKNOWN_TOPIC_OR_PARTITION`. Before, `postgres://`, `sqlite://` and `slatedb://` brokers closed the connection, and `memory://` and `s3://` brokers waited out `max_wait` and then answered with no error. A fetch that names only unknown topics answers at once; one that also names an existing topic waits for that topic's data as usual. A fetch by topic id for an id that doesn't exist gets its requested id back instead of the null id, so a Java consumer on a deleted topic refreshes its metadata instead of fetching again ([#834](https://github.com/nisshi-io/nisshi/pull/834)).
- On S3, in-memory and SlateDB storage, a fetch offset inside a batch returns that batch, as Kafka does. Before, the records from that offset to the next batch were unreachable, and a consumer positioned inside a partition's last batch polled empty forever ([87db6ea](https://github.com/nisshi-io/nisshi/commit/87db6ea154e1bf792418ecae522cf953b59b5d21)).
- On PostgreSQL, SQLite and Turso, Fetch returns batches with the producer's compression codec instead of uncompressed, and no longer runs one query per record after `max_wait`, which made some consumers time out and retry forever ([#734](https://github.com/nisshi-io/nisshi/pull/734)).
- PostgreSQL Fetch no longer withholds committed records while an unrelated transaction is open in the database ([#713](https://github.com/nisshi-io/nisshi/pull/713)).
- `read_committed` consumers on PostgreSQL, SQLite and Turso no longer read past the last stable offset into open transactions ([#689](https://github.com/nisshi-io/nisshi/pull/689)).
- On PostgreSQL, a repeated EndTxn no longer writes a second marker, and a repeated AddPartitionsToTxn is a no-op instead of closing the connection ([#712](https://github.com/nisshi-io/nisshi/pull/712)).
- Fetch answers `UNKNOWN_TOPIC_OR_PARTITION` for a partition index the topic doesn't have, before any storage read, as Kafka does. On PostgreSQL, SQLite, Turso and SlateDB the broker closed the connection. A partition that storage reports unknown, because its topic was deleted between the metadata and storage reads, is answered the same way on the object store engines and SlateDB. On S3 and in-memory storage, ListOffsets answers a partition that doesn't exist with `UNKNOWN_TOPIC_OR_PARTITION` and offset -1 instead of `NONE` and offset 0 ([#1000](https://github.com/nisshi-io/nisshi/pull/1000)).
- An `OffsetCommit` from a member that another broker removed from the group is no longer stored. The commit is checked against the group in storage, and the group is written before the offsets ([#990](https://github.com/nisshi-io/nisshi/pull/990)).
- ListOffsets by timestamp now answers offset -1 and timestamp -1 with error NONE when no record has a timestamp at or after the target, as Apache Kafka does. The broker answered offset 0 before. That made the Java consumer's `offsetsForTimes()` throw `IllegalArgumentException: Invalid negative timestamp`, and it sent a client that seeks to the returned offset back to the start of the partition. A partition answered with an error code now also carries offset -1 instead of 0 ([#838](https://github.com/nisshi-io/nisshi/pull/838)).
- On S3 and in-memory storage, ListOffsets by timestamp answers the first record whose own timestamp is at or after the target. It matched object write times, used `>` instead of `>=`, returned a batch's base offset, and listed every batch of the partition on every call. A batch it cannot read answers `KAFKA_STORAGE_ERROR` for that partition ([#840](https://github.com/nisshi-io/nisshi/pull/840)).
- InitProducerId v0 to v2 works on every storage engine. These versions do not carry a producer ID or epoch. PostgreSQL, libSQL and Turso panicked on them, and on a KIP-360 epoch bump, ending the connection. The object store engines (`memory://`, `s3://`, `gs://`) answered `UNKNOWN_SERVER_ERROR`, and so did SlateDB without a transactional ID ([#712](https://github.com/nisshi-io/nisshi/pull/712), [#887](https://github.com/nisshi-io/nisshi/pull/887)).
- On PostgreSQL, concurrent InitProducerId requests for one transactional ID bump its epoch one at a time. Before, two of them could both succeed, and one could fail with a storage error ([#887](https://github.com/nisshi-io/nisshi/pull/887)).
- IncrementalAlterConfigs `APPEND` and `SUBTRACT` on a topic no longer panic the connection on the PostgreSQL, SQLite, Turso, S3 and in-memory engines, and are no longer ignored on SlateDB ([#888](https://github.com/nisshi-io/nisshi/pull/888)).
- An OffsetFetch whose storage fails no longer panics the connection. The response reports `COORDINATOR_NOT_AVAILABLE`, which clients retry, for a transient failure, or the storage's own error code. From version 8 each group reports its own error, and the other groups still get their offsets ([#888](https://github.com/nisshi-io/nisshi/pull/888)).
- DescribeConfigs for a `BROKER` resource works on PostgreSQL, SQLite and Turso (`kafka-configs --entity-type brokers` failed with `UNKNOWN_TOPIC_OR_PARTITION`), and a name other than empty or the node id gets `INVALID_REQUEST` on every engine, as in Kafka ([#998](https://github.com/nisshi-io/nisshi/pull/998)).
- CreateTopics rejects a `replication_factor` of 0 or below -1 with `INVALID_REPLICATION_FACTOR` (38), as Apache Kafka does. -1 still selects the default (1) ([#829](https://github.com/nisshi-io/nisshi/pull/829)). A factor of -2 or less stored by an earlier version no longer panics Metadata or DescribeTopicPartitions ([#996](https://github.com/nisshi-io/nisshi/pull/996)).
- On S3 and in-memory storage, a failed record write no longer leaves the producer's sequence advanced, which made its retry look like a duplicate and lost the batch. A failed EndTxn retry now writes the missing markers, and a DeleteTopics that fails part-way can be retried ([#805](https://github.com/nisshi-io/nisshi/pull/805)). A batch rejected for a decode or schema failure no longer advances the sequence either ([#853](https://github.com/nisshi-io/nisshi/pull/853)).
- `nisshi proxy`'s batch combiner keeps each record's timestamp when the batches it combines have different base timestamps ([#841](https://github.com/nisshi-io/nisshi/pull/841)).
- PostgreSQL `create_topic` no longer reports success for a topic whose partition or watermark rows were not written ([#929](https://github.com/nisshi-io/nisshi/pull/929)).
- PostgreSQL DeleteTopics no longer scans the whole `record` table, which could make it time out on a large database ([#983](https://github.com/nisshi-io/nisshi/pull/983)).
- On SQLite, a pooled connection left inside an open transaction is discarded instead of holding the write lock for the next request ([#975](https://github.com/nisshi-io/nisshi/pull/975)). A panic or cancelled request no longer stops every later storage request; 0.6.0 always ran in what is now `mpsc` mode, and the new default, `semaphore`, was never affected ([#836](https://github.com/nisshi-io/nisshi/pull/836)).
- libSQL and Turso recover consumer group state after a restart instead of failing to read it ([#662](https://github.com/nisshi-io/nisshi/pull/662)).
- SlateDB: concurrent requests for one group, or the first request after a restart, no longer drop the group's members ([#763](https://github.com/nisshi-io/nisshi/pull/763)).
- On SQLite and Turso, the first record of a fetch after compaction keeps its own headers.
- A Snappy batch with a truncated xerial header is rejected with an error instead of panicking the decoder ([#821](https://github.com/nisshi-io/nisshi/pull/821)).
- A compressed record with an overlong varint fails to decode instead of panicking or decoding to a wrapped value ([#908](https://github.com/nisshi-io/nisshi/pull/908)).
- A JoinGroup with an empty protocol list gets `INCONSISTENT_GROUP_PROTOCOL` instead of panicking the connection ([#728](https://github.com/nisshi-io/nisshi/pull/728)).
- Followers that join or sync before the leader has sent its assignment wait for it, instead of getting an empty assignment that made franz-go fail with "response did not contain enough data to be valid" and caused continuous rebalances ([#680](https://github.com/nisshi-io/nisshi/pull/680)).
- SASL re-authentication on an existing connection ([KIP-368](https://cwiki.apache.org/confluence/display/KAFKA/KIP-368%3A+Allow+SASL+Connections+to+Periodically+Re-Authenticate)) works. Long-lived Java clients failed with "Client SASL mechanism ... not enabled" ([#665](https://github.com/nisshi-io/nisshi/pull/665)).
- A transient `accept()` error no longer stops a listener accepting connections ([#727](https://github.com/nisshi-io/nisshi/pull/727)).
- Optional tagged fields that a negotiated version does not support are no longer encoded, which produced invalid responses such as FetchResponse v12 with node endpoints.
- `nisshi proxy` and the CLI tools no longer reuse a connection to the broker that the broker closed, that has bytes nobody read, that was idle for more than 9 minutes, or whose last request failed, timed out or was cancelled. Such a connection could fail the next request, or give it the response to an earlier one ([#885](https://github.com/nisshi-io/nisshi/pull/885), [#882](https://github.com/nisshi-io/nisshi/issues/882)).
- `nisshi cat`, `nisshi-generator`, `nisshi-perf` and the proxy's batch combiner set `last_offset_delta` correctly ([#783](https://github.com/nisshi-io/nisshi/pull/783)).

### Security

- SCRAM authentication with a wrong password no longer authenticates the connection. The broker treated any finished SASL exchange as authenticated, including one whose client proof did not verify ([#696](https://github.com/nisshi-io/nisshi/pull/696), [#694](https://github.com/nisshi-io/nisshi/issues/694)).
- `nisshi proxy` no longer forwards SASL requests over its shared connection pool, where one client's login applied to every later client of the same pooled connection ([#993](https://github.com/nisshi-io/nisshi/pull/993)).
- `--cert` and `--key` together now make the listener TLS-only. In 0.6.0 the two flags together were rejected as conflicting, a single flag was ignored, and the broker dropped any TLS configuration, so it only ever served plaintext ([#735](https://github.com/nisshi-io/nisshi/pull/735)).
- Decoding a produce batch is bounded. Previously a few KB of compressed data could decompress into gigabytes, and a record carrying millions of empty headers expanded 32x on decode. Now a batch is rejected with `MESSAGE_TOO_LARGE` once its decompressed bytes, or its decoded records and headers, pass a 100 MiB budget, or up front when its `record_count` alone would. A producer can recover by splitting the batch (the Java producer does this on its own for a batch of more than one record). Peak memory while decoding one batch is a small multiple of that budget (roughly 2 to 3x), not 100 MiB exactly:
  - an uncompressed record's headers are charged after they are allocated, so the record that crosses the budget can add up to about 100 MiB more;
  - a Snappy batch holds its decompressed block (up to 100 MiB) alongside the records decoded from it;
  - zstd's decoder window, up to 128 MiB, sits outside the budget.

  The budget applies per batch; concurrent batches each have their own ([#821](https://github.com/nisshi-io/nisshi/pull/821)).
- Counts and lengths read from the wire are checked before they size an allocation. A `record_count` near `u32::MAX` aborted the broker, and a negative batch length or header count panicked the connection ([#782](https://github.com/nisshi-io/nisshi/pull/782)). A record's fields are read within its declared length, so a bad header count no longer reads into the next record ([#831](https://github.com/nisshi-io/nisshi/pull/831)).
- A request's length-prefixed fields are bounded by the frame's own size, and before authentication a request the client may not send yet is rejected by its API key before its body is decoded. A 24-byte frame could ask for a 1 GiB allocation ([#823](https://github.com/nisshi-io/nisshi/pull/823)). A frame's 4-byte length prefix could make the broker or proxy allocate 2 GiB per connection, or panic on a negative value ([#723](https://github.com/nisshi-io/nisshi/pull/723)).
- A listener with SASL configured closes a connection that sends a frame larger than 512KiB before the client authenticates, matching the Apache Kafka default for `sasl.server.max.receive.size`. The same limit applies while a client re-authenticates. The broker logs this rejection as `PreAuthenticationFrameTooBig`, and counts it in `nisshi_frames_rejected` ([#823](https://github.com/nisshi-io/nisshi/pull/823)).
- Produce rejects a client batch with the control bit set, which bypassed schema validation and lake writes and looked like a transaction marker to consumers ([#795](https://github.com/nisshi-io/nisshi/pull/795)).
- On S3 and in-memory storage, Produce answers `UNKNOWN_TOPIC_OR_PARTITION` for a topic or partition that doesn't exist and writes nothing. A produce to a crafted topic name could write into another topic's keys and make every Fetch of it panic ([#977](https://github.com/nisshi-io/nisshi/pull/977)).
- On S3, Google Cloud Storage and in-memory storage, a Fetch for partition indexes a topic doesn't have no longer caches a watermark for each one, which let a client grow the broker's memory without bound. DeleteTopics also drops the topic's cached watermarks on the broker that handles it ([#1000](https://github.com/nisshi-io/nisshi/pull/1000)).
- A `tansu.lake.generate.*` topic config must be `CAST(<column> AS DATE|INT|INTEGER)`. Any other expression inside a `CAST` was executed by DataFusion during Delta Lake writes, and a value that wasn't a `CAST` panicked the write ([#745](https://github.com/nisshi-io/nisshi/pull/745)).
- Logs write `[hidden]` in place of SASL auth bytes, SCRAM salted passwords, delegation token HMACs, stored SCRAM keys, and config values in `AlterConfigs` and `IncrementalAlterConfigs` requests, at every log level. Frames, record batches, record keys and values, and record header values are logged with the length of their bytes, not the bytes. SQL statements are logged without their parameters, and schema validation and lake conversion log the field and the kind of value, not the value ([#889](https://github.com/nisshi-io/nisshi/pull/889)). A password in the `user:password@` part of a storage, schema registry or lake URL is removed before logging; one given as a `?password=` query parameter is not ([#747](https://github.com/nisshi-io/nisshi/pull/747)).
